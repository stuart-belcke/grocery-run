Grocery Run — Roadmap
=====================

A single, prioritized backlog combining the earlier scattered notes with the
newer batch of ideas. Duplicates and closely-related items have been merged.
Tiers are ordered: cheap high-impact UX wins first, then the Ingredients-tab
cluster (which shares a refactor), then data-model changes, then the riskier
multi-device / integration work last. A Hygiene section after Tier 4 collects
the work that isn't a feature — tests, shared logic, and the database seam.


Tier 1 — small, high-value, low-risk
------------------------------------
1. [DONE — #11, #12] Recipe detail view. Tapping a recipe card in the Meals
   tab expands its full ingredients + notes, read-only, without having to hit
   Edit.
2. [DONE — #11] Remove a meal from "the list". After "Add to list" from the
   Meals tab, give an explicit way to take it back off. Also handle meals that
   reached the list via the Week plan, not just the Meals tab.
3. [DONE — #11] Suggested "unit" values when adding a new item.
4. [DONE — #11] Move the settings section off the bottom of the Ingredients
   page into a dedicated Settings tab (or a hamburger menu at the top). Do
   this before adding search/filter to the Ingredients tab so it isn't
   cluttered.
5. [DONE] Checked-off items: gray only the name, not the details. The whole
   List row no longer dims on check — only the item name gets the
   strikethrough + dim, so expanding a checked item keeps its "On the list
   for" breakdown at full opacity and legible.
6. [DONE] Week-plan meal picker. Each day/meal slot is now a tap-to-open
   button (showing the assigned meal, or "＋ Choose a meal") that opens a
   searchable modal mirroring the Meals tab — a search box plus recipes
   grouped "{type} meals" / "Other meals", each showing servings + tags, with
   the current pick checked and a "Remove meal from this slot" option. Replaces
   the native <select> that didn't fit the app's feel or scale with the list.


Tier 2 — Ingredients-tab cluster (shared refactor, then features)
-----------------------------------------------------------------
7. [DONE] Ingredients tab row treatment. Each row now collapses to just the
   ingredient name (with a subtle default-store · aisle hint), a gear, and an
   X. Tapping the gear or the name expands the row to edit the default store
   and per-store aisle numbers; Rename lives inside that expanded panel.
8. [DONE] Make the Ingredients tab filterable by store and A-Z, and add
   search. A search box (name match, with a clear ✕, mirroring the Meals tab)
   plus a store-filter dropdown ("All stores" / each store / Unassigned) that
   narrows to items with that default store. List stays A-Z sorted.
9. [DONE — #17] Ingredient rows show which recipes they're used in (inside
   the expanded gear panel, alongside whether it's also hand-added to the
   list) rather than as a separate info icon.
10. [DONE — #17] Add ingredients to the shopping list straight from the
    Ingredients tab. Each row gets a "+ List" button that becomes a
    ± quantity pill (with a tap-to-type-exact-amount) once it's on the list,
    defaulting to whatever unit recipes most commonly measure it in.
11. [DONE — #17] The List tab's "add an item" field now suggests matching
    known ingredients as you type (name + default store, keyboard-navigable),
    so you pick an existing item instead of creating a duplicate.
12. [DONE] Suggest units as you type when adding a new ingredient.
    Both halves are built — the conversion table first, the suggestions after.

    What shipped: a factor table in lib.js grouping units by dimension, and
    resolveAgainstBought doing the cupboard subtraction in base units so
    buying 1 lb offsets a recipe asking for 16 oz. That was the costly bug —
    the item stayed on the list looking unbought and you bought it twice.
    Amounts that can be added are added (1 lb + 8 oz reads 1.5 lb), and
    commonUnitFor now weighs by dimension so one "can" can't outrank an lb
    and an oz that between them say this is measured by weight.

    Two decisions worth keeping:
      - PROMOTION NEVER CROSSES MEASUREMENT SYSTEMS. Display picks the largest
        unit that keeps the number at or above 1, stepping down when it would
        fall below: 24 oz reads 1.5 lb, 1500 g reads 1.5 kg, a quarter pound
        reads 4 oz. It will promote to a unit nobody typed, because g/kg and
        oz/lb are one scale that everyone reads at a glance. It will NOT cross
        between them — answering "how much flour" in a system this household
        doesn't use is the surprise actually worth avoiding, and that is the
        one thing the metric/standard setting (item 31) would authorise.
        Two carve-outs, both learned by looking at the output:
          pt / qt / gal convert but are never promotion TARGETS. They're
          container sizes; a recipe wanting 2 cups of stock read "1 pt".
          Count units don't promote at all and show in the SMALLEST unit used:
          a dozen eggs plus two more is "14 ea", not "1.17 dozen".
      - US factors are defined from their exact ratios (1 lb = 16 oz, 1 cup =
        16 tbsp, 1 tbsp = 3 tsp) rather than via the metric base, so 16 oz and
        1 lb compare exactly instead of missing by a float hair and leaving
        0.0001 lb on the list.
    An amount with qty 0 ("salt, to taste") is kept at zero rather than
    dropped — an empty group is not the same as a covered one.

    [DONE] The suggestion half. Extended to every place a unit is typed — the
    recipe editor's ingredient row, the List tab's add box, and the amount
    editor on Ingredients.
    THE INGREDIENT'S OWN UNITS COME FIRST, and that is the only reason this is
    worth more than the flat list it replaces. Typing a unit for garlic offers
    `cloves` — twelve recipes use it — before `cup`, which is merely the
    household's commonest. The flat A-Z list was technically correct and went
    unused because the obvious answer was nine rows down.
    Ranked: this ingredient's units, then everything the household has typed
    ordered by HOW OFTEN, then COMMON_UNITS. Typed text narrows by prefix
    before substring, so "c" leads with `cup` rather than `oz can`.
    THE LAST TIEBREAK IS unitSuggestions' OWN ORDER, not alphabetical — a
    brand-new household has no usage to rank by, and alphabetical had it
    offering "bag, box, bunch" ahead of "cup" and "lb". Caught by the test for
    a fresh household, which is the case nobody using the app is ever in.
    AND IT IS NO LONGER A <datalist>. Those render unreliably — frequently as
    nothing at all on a phone, which reads as "this app has no suggestions"
    rather than a browser quirk. That is the same reason the ingredient-NAME
    field grew a custom list (item 11); the units kept the datalist for
    another year. One <SuggestInput> in ui.jsx now serves all three, taking
    its suggestions as a prop so ui.jsx still knows nothing about units.
    SUGGESTS, NEVER RESTRICTS. An exact match offers nothing — handing back
    the word somebody just finished typing is noise and leaves a dropdown over
    the field they are trying to leave — and a unit nobody has used is typed
    and kept, which the e2e asserts on what was PERSISTED rather than on the
    field, because a box that accepts text and drops it on save looks
    identical while you type.


Tier 3 — data-model / sorting
-----------------------------
13. [DONE] Pantry staples — things you own, kept off the list until you run
    out. `config[key].staple` marks one; `stapleNeeds[key]` says you're out.
    Two decisions that shaped everything after:
      - NO PARALLEL DATA STRUCTURE. A staple is an ordinary ingredient with a
        flag. "The staples list" is only ever a VIEW. Nothing to migrate,
        nothing to keep in sync.
      - THE SPLIT BY LIFETIME, which later features copied: the designation is
        a durable fact about the kitchen and lives in the catalog; being out is
        trip state and lives in the shopping state. Only "need" entries are
        stored, so an all-clear state tidies itself away.
    A staple carries forward if you didn't buy it, rather than needing
    re-entry — that is why it beats a weekly "what are we out of" prompt.

14. [DONE] Once an item is checked on the List, move it to the bottom of its
    group and keep following the A-Z / store-flow sort the user has selected.
15. [DONE] Recipes reference the shared ingredients list to avoid duplicates.
    The recipe editor's ingredient-name field now suggests matching known
    ingredients as you type (name + default-store hint, keyboard-navigable),
    reusing item 11's List-tab pattern, so you pick an existing item's exact
    spelling instead of forking a spelling variant into a separate ingredient
    and shopping-list line. Recipe ingredients still store { name, qty, unit };
    the suggestions steer them onto canonical norm(name) identities.


Tier 4 — multi-device / integrations (highest risk, do last)
------------------------------------------------------------
16. [DONE — by items 37, 41 and 48, and NOT in the shape written here]
    "Formalize create/join household. Household codes already exist under the
    hood; this makes creating or joining one a first-class flow."

    Both flows are first-class now:
      CREATE — the first-run screen's "Start my own list" mints a code and
        claims it, and the rules allow that claim exactly once (rules.test
        "a brand new household can be claimed, and only once").
      JOIN — a tapped invite LINK fills the field on first run, and Settings
        carries the same field for a device already in use, alongside the
        member list, invites, revoke and remove.

    THE REASON THIS IS WORTH READING RATHER THAN JUST TICKING: what shipped
    deliberately contradicts the sentence above. This item assumed the CODE
    was the mechanism to formalise — "household codes already exist under the
    hood" — and the code is no longer a credential at all. Knowing one gets
    you nothing (item 42; rules.test "knowing the code is not enough — a
    stranger is refused"); joining needs an invite from someone already in,
    redeemed for an ACCOUNT. The code became an address. Formalising
    code-based joining would have shipped the security hole this app then
    spent items 37/42/48 closing.

    ITS DEFERRAL REASON IS ALSO GONE. The note that used to sit here said 16
    and 17 were "patches on top of a catalog that can't be written at
    runtime". The catalog IS written at runtime now, per household
    (sync.js writeCatalog -> households/{code}/catalog), and the override
    layer that existed only because it couldn't be is deleted outright — see
    item 37's "ALREADY DONE" list. Nothing here is blocked on that any more,
    which applies to 17 as much as to 16.

17. [DONE] Delete / log out of households, and clean up orphaned data.

    THE HOLE THIS TURNED OUT TO BE, measured against the real rules on the
    real emulator rather than reasoned about:
      - a member could already LEAVE (the rules allow deleting your own
        record), but nothing in the UI offered it;
      - a household with no members is claimable again BY DESIGN — a new
        code has to become somebody's somehow — and the rules comment called
        that "abandonment, not a back door";
      - but the STATE AND CATALOG SURVIVED the last member leaving. So
        anyone who still knew the code could claim the empty household and
        read the shopping list, the week plan and every recipe.
        Confirmed, not inferred: claimed true, read state true, read catalog
        true. Abandonment did not mean empty; it meant unguarded.
    Not guessable — a code is 13 characters of [a-z0-9-] — so the realistic
    holder of one is a REMOVED MEMBER, an expired guest, someone who saw a
    screenshot, or an old phone of your own. Which is the whole population
    item 37's removal work exists to keep out.

    THE FIX IS THAT THE LAST ONE OUT TAKES THE DATA WITH THEM.
    leaveHousehold (sync.js) reads the member list, and if nobody else is
    there deletes households/{code} outright instead of just its own record.
    Now abandonment means empty, and the claimable-empty-code behaviour the
    rules always intended is what actually happens.
    NO RULES CHANGE WAS NEEDED — a full member could already delete the node;
    it was never wired up. That is the best outcome available on the one file
    in this repo nothing else executes.

    THE ORDER IS FORCED, NOT CHOSEN: `.read` requires a membership record, so
    the instant your record is gone you can no longer see whether anyone else
    remained, nor delete anything. Check-then-act is the only shape that
    exists here; act-then-check locks you out of the check.

    WHAT A GUEST CAN AND CANNOT DO, and the rules were already right: a guest
    may leave, but may not delete the household — deleting reaches the
    catalog and the week plan, exactly what the guest role withholds. A guest
    who is somehow the last one out leaves the node behind and the app SAYS
    so rather than swallowing it.

    ONE RACE, ACCEPTED AND WRITTEN DOWN: two members leaving in the same
    instant can both see the other and both remove only themselves. Closing
    it would need a transaction across a node the leaver is about to lose
    access to. The cleanup script is the answer to that residue.

    FOUR NEW RULES TESTS pin the guarantees the app now leans on: the last
    member can delete the node, a guest cannot, a stranger cannot, and — the
    one that keeps the bug from coming back — an emptied household leaks
    nothing to whoever claims the bare code next. 47/47.

    RECLAIMING THE ONES ALREADY OUT THERE CANNOT BE A BUTTON, and that is
    structural rather than lazy: finding an abandoned household means listing
    /households, which nothing may do (that denial is what stops one grant
    exposing every household at once), and a client cannot read a household
    it is not a member of — which is precisely what an abandoned one is. So
    scripts/reclaim-households.mjs runs by hand with a service-account key,
    lists households shallowly, and deletes the ones with no members. Dry run
    is the DEFAULT; --delete is opt-in; it prints each household's last write
    date before removing it so a mistake is visible in the log rather than
    silent. No new dependency — it signs its own JWT with node:crypto and
    drives the REST API, the same choice tests/rules/harness.mjs made.
    IT IS TESTABLE, which mattered more than it sounds: pointed at
    127.0.0.1 it skips the Google token exchange and uses the emulator's
    owner credential, so "which households are abandoned" can be proved
    somewhere other than the one database where a wrong answer deletes
    somebody's recipes. Verified: 4 seeded households, 2 with members
    (one of them a guest) kept, 2 orphans found by the dry run and removed
    by --delete, nothing left behind.

    NOT VERIFIED IN A BROWSER, plainly: the Leave button lives behind
    `user && !accessDenied`, and a real signed-in user only exists behind
    real Firebase Auth — the e2e build compiles sync out entirely. Same
    documented gap as invite creation (item 68) and redemption
    (invitelink.spec.mjs). What IS proved is the half that decides whether
    data is exposed: the rules, on the real emulator.
    The service-account path of the script is likewise unrun — there is no
    key here — so only its emulator path has been executed.

    AND THE UNTESTED HALF WAS BROKEN, WHICH IS WHY THAT CAVEAT IS WORTH
    WRITING DOWN RATHER THAN HEDGING WITH. Reported from the preview build:
    "Leave just seems to create a new household."
    It did. Leaving removed the member record and deleted the old node
    correctly — and then the device rebuilt an identical household under a
    fresh code, because switching to a brand-new code takes the seed path:
      App.jsx  if (user && code) recordHouseholdMembership(code, user)
      App.jsx  } else if (push) { writeHousehold(code, localRef.current) }
    A new code has no remote state, so `push` is true and the device
    uploads whatever it is still holding — which is the household you just
    walked out of. Net effect: nothing appeared to happen, and for the last
    member the promise that the recipes were deleted was undone seconds
    later by re-uploading them under a new name. The dialog said "a fresh
    household of its own"; what shipped was a clone.

    THE FIX IS ORDERING, and it works because localRef/hCatalogRef are
    assigned during RENDER rather than in an effect: resetting the local
    state and the catalog in the SAME handler as setCode means both setters
    and the code change land together, so the subscribe effect re-runs
    already holding an empty state and seeds the new household with that.
    forgetHouseholdCache also drops the old code's two localStorage copies —
    the caches are keyed by code, so without it the household you just left
    stays on the phone in full, invisible but restorable by typing the old
    code back in. "Left" has to mean gone from here too.

    STILL NOT REPRODUCIBLE IN THE HARNESS, and that is the actual lesson:
    the whole flow needs a signed-in user AND the household UI, which the
    local-only build compiles out — so neither the bug nor its fix can be
    covered by a test here. This is the second bug in a row to land in the
    auth-gated half of the app. The gap is not "some UI is untested", it is
    that a WHOLE INTERACTION MODE has no coverage, and both bugs were in it.
    Worth its own item rather than another caveat: a preview seam for a
    signed-in user, the way GUEST_PREVIEW_KEY already fakes guest-ness for
    the tests that need it.

18. Export to / link with a Google calendar, keyed off the household.


Hygiene — not features, and not sequenced
------------------------------------------
None of these ship anything on their own. They're what keeps the app cheap to
change: a test layer, one place for shared logic, and a database seam narrow
enough to swap what sits behind it. Do them alongside whatever feature is next
rather than saving them for a cleanup that never gets scheduled.

19. [DONE] Tests on the pure layer. `npm test` runs node's built-in runner
    over lib.js — 100+ tests, no framework installed. CI runs lint, tests and
    build before deploying, in that order, so a failure stops the deploy rather
    than annotating one that already shipped.
    MUTATION-TEST ANYTHING LOAD-BEARING: break the rule deliberately, confirm
    the right tests fail, restore. A test that passes either way protects
    nothing, and several here originally did.

20. [DONE] Make a failed write visible. A rejected write used to be
    console.error and nothing else — invisible on a phone, where there is no
    console. Both writeHousehold and writeCatalog now report through a small
    pub-sub in sync.js (watchWriteErrors), which App.jsx subscribes to and
    reuses the SAME dot/label the offline state already draws with — no new
    visual language, just a truthful reason attached to the existing one.
    Offline is deliberately NOT this: the SDK queues writes in memory and
    flushes on reconnect without ever rejecting, so the signal only fires when
    the server actively refuses a write while connected (rules, quota, a
    malformed payload). Self-correcting, same shape as the update gate: it
    clears the moment any write succeeds again, no dismiss button needed.
    Done together with item 33 — same file, same theme, and fixing 33 first
    made 20 land on writes that no longer intermittently reordered anyway.

21. Keep the database seam narrow. Every database call lives in sync.js, and
    App.jsx is the only component that touches sync at all (SettingsTab
    imports syncEnabled, and nothing else — cleanCode moved to lib.js when
    parseInvite needed the same alphabet, which narrowed this further; the
    invite and member calls it needs arrive as props). That
    property, not any clever abstraction, is why RTDB could be swapped for
    Firestore in days rather than weeks. Defend it deliberately as usage
    grows and the right database stops being obvious:
      - no `firebase/*` import outside sync.js. Add an ESLint
        no-restricted-imports rule so it can't regress silently.
      - the seam should say WHAT CHANGED, not hand over everything.
        toggleChecked(key, on), not writeHousehold(entireState). RTDB
        implements that as a write at one path; Firestore as a document
        update. Neither is forced into the other's shape.
      - this also retires the update() footgun. Two update() calls in one
        handler discard the first, because both rebuild from the same stale
        snapshot — that is what broke the staple checkbox, and a comment on
        the function is not enforcement. Narrow writes remove the constraint
        instead of documenting it.
      - do NOT abstract queries or offline storage. Those genuinely differ
        between the two databases and a wrapper inherits the weaknesses of
        both. Keep filtering in JavaScript, and keep loadCache/saveCache as
        thin as they are — a Firestore migration deletes them outright rather
        than porting them.

    THE READ HALF IS STILL OPEN, AND IS DELIBERATELY DEFERRED. Narrow writes
    shipped; narrow listeners did not. One onValue at `state` delivers the
    WHOLE subtree however deep the write was, so every remote change
    re-normalizes the entire structure and re-renders everything.
    DO NOT DO THIS YET. Item 25's measurement killed the case for doing it now:
    the whole synced node is 954 BYTES, so the widest possible listener
    delivers under a kilobyte, and re-normalizing that plus a re-render is not
    worth a refactor that breaks four things (below).
    THE CATALOG MOVE WAS PREDICTED TO BE THE TRIGGER, AND IT WASN'T. This entry
    used to say the move would take the listened-to node from ~1 KB to ~30 KB
    and finally make the four costs worth paying — "do it immediately after
    that move, not before". The move shipped and that never happened, because
    the growth landed on its OWN node (households/{code}/catalog) rather than
    inside `state`. The listener at `state` still delivers about a kilobyte.
    The move made this case WEAKER, not stronger; item 37's "what's left"
    records the same conclusion from the other direction.
    THE REAL TRIGGER IS MEASURABLE, NOT ARCHITECTURAL: `state` itself getting
    big — per-person data, trip history, anything that stops it being one
    shared list — or re-render jank someone can actually feel on a phone.
    Re-measure with item 25's method before acting on it. Predicting this one
    by reasoning about the architecture is exactly what just went wrong.
    What it costs, so it isn't a surprise:
      - the atomic snapshot. Branches start arriving independently and out of
        order instead of as one coherent state.
      - pickState as written. It compares ONE updatedAt for the whole blob to
        decide local-vs-remote at launch; per-branch updates need per-branch
        stamps or a different staleness rule.
      - "is this a new household?", which today is just remote === null at the
        state node and drives the seeding path.
      - normalizeLocal splits into per-branch normalizers. That is where it
        should end up anyway, but it is work.
    Related measurement in item 25 — informative, not a gate.
    Background in FutureProjects.md ("Per-user catalog").

    UPDATE, once the catalog move shipped: the catalog went to its OWN node
    (households/{code}/catalog) with its OWN listener and its OWN updatedAt,
    not into the state node. So the ~30x growth this item was waiting for
    never lands on `state` — it lands next to it, already split. Ticking a
    checkbox still delivers under a kilobyte, and editing a recipe delivers
    the catalog without touching the list.
    That is one branch of the per-branch split this item describes, done for
    the branch that actually needed it, and it cost none of the four things
    above: each node keeps its atomic snapshot, keeps a single updatedAt that
    pickState reads unchanged, and keeps "remote === null means seed me".
    What remains open is splitting the STATE node itself (list vs plan vs
    stapleNeeds), and the case for that is still weak at 954 bytes. The next
    real trigger would be a third party in the household, not size.

    The adopt-vs-push rule is now shared. Both nodes route their listener
    through the same pickState: newer stamp wins, ties go to remote so two
    phones don't bounce a value between them, and no remote at all means
    seed. The catalog needed it for a specific reason — updateCatalog can't
    write before the listener has reported (writing early could replace a real
    catalog with a locally seeded copy), so an edit made offline sits on disk
    unwritten, and adopting on connect would silently discard it. A pristine
    seed carries updatedAt 0 precisely so it can never win that comparison;
    only an actual edit stamps a real time.

22. [DONE] List-building logic moved out of the tabs into lib.js. The tabs
    were 600-750 lines each, mixing data logic with rendering, and none of it
    was testable. Everything with a rule in it — aggregation, filtering,
    sectioning, unit conversion, ingredient identity — now lives in lib.js and
    is covered by item 19's suite.

23. [DONE] Ingredients have a stable id. The key used to BE the name, so
    renaming orphaned every reference — and two were already being lost in
    practice, because list.bought and stapleNeeds were added after the rename
    code was written and nobody went back.
      ingredients: { ing_7f3a2b: { name, store, aisles, staple } }
      recipe lines: { ingredientId, qty, unit }
    THE FILE STAYS NAME-KEYED. catalog.json is hand-edited and diffed in git;
    ids in it would mean inventing one and matching it across two sections just
    to add a recipe. Minted on the way in, resolved back to names on export.
    THE TRICK THAT KEPT IT SMALL: App resolves each line's id to a name when it
    assembles `data`, so every tab that reads i.name was untouched.
    Reads still accept a legacy norm(name) reference — expand phase. THE
    CONTRACT PHASE IS STILL TO DO: drop that fallback once both phones have run
    the migration and been used for a few days.
    The migration fires from the catalog LISTENER, never at startup. Converting
    offline would let a device mint ids, remap its state onto them, then adopt
    the other phone's catalog with DIFFERENT ids and orphan everything. Exactly
    one authority converts.

    TWO BUGS FOUND BY USING IT, NOT BY TESTS — both "code written when the key
    WAS the name":
      1. Four places read a key and treated it as a name. Two rendered
         "Ing_c45b0s82" where a name belonged; worse, the Ingredients add box
         and the recipe editor WROTE name-keyed entries into an id-keyed
         catalog, which would have reintroduced the old shape one entry at a
         time while looking fine. Everything that turns a typed name into an
         ingredient now goes through ensureIngredientId; everything that
         displays one uses ingredientNameFor.
      2. Renaming onto an existing name created a DUPLICATE. Impossible while
         the key was the name, and the old rename merged instead — a rule
         dropped along with the key-moving it needed. Renaming now merges,
         repoints recipes, sums a line that would otherwise duplicate, and asks
         first because a merge deletes an ingredient.
    THE LESSON: the migration was correct both times. What broke was ordinary
    EDITING afterwards. A migration test that only checks the conversion misses
    this entire class.

24. [DONE] Concurrently-edited collections are keyed by identity, not arrays.
    An array index is not a stable identity: two phones appending at once
    collide, and neither database can address one element without rewriting the
    whole list. diffPaths treats arrays as ATOMIC for that reason, so a keyed
    object is what makes a narrow write possible at all.
    Stores stay an array deliberately — order is meaningful (it drives
    store-flow grouping) and they're edited about never.
    Accepting the legacy shape on read is permanent, not transitional: Firebase
    hands arrays back as index-keyed objects regardless.

25. [DONE] Measure the wire. Two browser windows, DevTools on the WebSocket
    frames. The finding killed a planned optimisation: the whole synced node
    was 954 BYTES, not the ~30 KB assumed, because the catalog wasn't in it.
    A checkbox tick is ~130 bytes. Re-measure after any change that moves data
    into the synced node — arguing from an imagined payload size wasted a day.

26. [DONE] Week starts Sunday, not Monday — and make it a setting rather than a
    constant. DAYS is hardcoded in lib.js, so this is a small change to the
    array plus a place to choose. That place doesn't exist: the Settings tab is
    household sync and the publish flow, with no actual preferences section.
    Build the section first, then this is its first occupant. TIER 1.

27. [DONE] Sides on a dinner. A slot holds a main plus sides rather than one
    recipe. All of them feed the shopping list through aggregateItems, which
    already summed the same ingredient from several sources, so the list side
    needed nothing.
    Done AFTER the catalog move, deliberately — it changes the shape of a plan
    slot, and doing it first would have meant migrating that shape twice.
    Covered by tests/e2e/specs/sides.spec.mjs, added later — it shipped with
    no coverage at all, and the parts worth guarding turned out not to be the
    arithmetic but a side's LIFETIME: it belongs to the main it was chosen
    beside, dies with it, and is silenced with it by skipList. The 🥗 flag on
    a recipe only orders the picker; any recipe can be added as a side.

28. [DONE] Meals that don't feed the shopping list — leftovers, or a meal
    you're already stocked for. `skipList: true` on the slot, surfaced as
    "Already have the ingredients" on the slot's servings row.
    The label names the EFFECT, not one reason for it. Two list-facing walks
    honour it through one shared `slotFeedsList`; plannedMealCount deliberately
    does NOT, because a skipped meal is still a planned meal.

    A LOOKUP KEY WAS CONSIDERED AND REJECTED — write it down, because the idea
    sounds safer than it is and will come back. Putting a short key in the URL
    and resolving it to {code, token} requires a phone that is NOT YET A
    MEMBER to read that mapping, which means a WORLD-READABLE index of every
    live invite. Today nothing about an invite is publicly readable at all:
    `invites` .read requires membership, and the joining phone never reads
    one — the RULES check it when the member record is written, which is why
    the token alone is enough. A short key is also enumerable, so the index
    could be harvested. Shorter URL, strictly worse. The fragment already
    never reaches a server, so there is nothing to buy.

    THE TOKEN IS THE ONE THING THAT WAS ACTUALLY WEAK, and it was fixed here.
    It base36-encoded each random byte and concatenated pieces of 1 or 2
    characters. Measured over 200k tokens: digits 1-6 at ~9.4% EACH against
    ~1.43% for most letters, 4.60 bits per character where uniform base36
    gives 5.17, and adjacent characters correlated because where one piece
    ends depends on its value. Probably still ~90 bits — and "probably" is the
    problem for a credential.
    Now 22 characters drawn uniformly by REJECTION SAMPLING: 256 is not a
    multiple of 36, so bytes >= 252 are discarded rather than folded with `%`,
    which would make the first four letters likelier. Measured after: every
    character 2.76-2.79% against a uniform 2.78%, 5.170 bits/char, 113.7 bits.
    It moved to lib.js in the process — it is pure logic, and in sync.js it
    could not be tested at all. The test asserts the DISTRIBUTION, because the
    old one did not look wrong; it looked like a random string.

50. A GUEST LINK IS REUSABLE FOR ITS FULL HOUR; A FULL INVITE IS NOT.
    Both are the same mechanism and only the `role` field differs, so this
    asymmetry is accidental rather than designed.
    joinWithInvite DELETES the token after redeeming it, and that deletion is
    what makes an invite single-use — the rules do not enforce it. But
    `invites/$token` .write requires `role != 'guest'`, so a guest who has
    just joined cannot delete the token they used. The remove() is refused,
    the catch swallows it, and the link stays live until `exp`.
    A full invite makes the joiner a non-guest member, whose delete succeeds.
    NOT OBVIOUSLY WRONG — two helpers sharing one guest link is a reasonable
    thing to want — but it was not decided, and the FAQ said "works once",
    which was false for half the cases. The wording is fixed; the BEHAVIOUR
    is still undecided.
    IF IT SHOULD BE SINGLE-USE, the rules have to do it, not the client: a
    guest cannot be given blanket delete on invites without also letting them
    revoke everyone else's. The narrow grant would be "delete a token whose
    id equals the `invite` field on your own member record".

    REQUIRING AUTH FORCED APP WORK, and it is the more interesting half.
    Once a signed-out phone is refused everything, the app had three ways to
    lie about it:
      - THE GREEN DOT. syncStatus comes from watchConnection, which reads
        .info/connected — a client-side path NO security rule gates. It
        reports "synced" perfectly happily while every read is refused, so
        a signed-out phone would have shown "Synced" over a dead listener.
        That is precisely the "looks fine, syncs nothing" failure this
        codebase keeps paying for. The precedence now lives in
        syncIndicator() in lib.js: sign-in state and authorization both
        outrank connection state, and connection is LAST because it's the
        one the database can contradict. Each case is the CAUSE of the ones
        under it — "Sign in to sync" says what to do, where "No access",
        equally true at that moment, leaves you guessing.
      - A SILENT DENIAL. onValue had no cancel callback, so permission_denied
        did nothing at all — indistinguishable from "connected, nothing has
        changed yet". subscribeHousehold/subscribeCatalog/subscribeMembers
        now take onError. Two properties matter: Firebase REMOVES a listener
        it cancels, so a denial is terminal and only a resubscribe recovers;
        and cb is never called on a denial, so a refused read can't arrive
        as `null` — which would read as "no household here, seed it" and
        turn a permissions problem into a write.
      - THE COPY. Settings still said sign-in was "optional, and doesn't
        change anything yet". It is now the thing that grants access.

    matters most — a socket genuinely CONNECTED while reads are refused —
    cannot be reproduced in a browser here, because this sandbox can't reach
    Firebase at all and the socket just reads offline. A pure function takes
    no network. Six tests cover it, and both mutations were confirmed:
    moving the "synced" check above the authorization checks fails exactly
    the three tests about precedence, and dropping the authReady guard fails
    exactly the one about not claiming "signed out" before auth has
    answered.
    authReady exists because `user === null` means two opposite things —
    "don't know yet" before Firebase answers, "nobody" after. Auth restores
    asynchronously, so treating the initial null as signed-out would flash
    "Sign in to sync" on every launch of a signed-in phone.

    [BUILT, NOT YET DEPLOYED] INVITES — the step that makes removing

    [BUILT, NOT YET DEPLOYED] THE GUEST ROLE. Someone you hand a link to so
    they can do the shop: reads everything, writes only the List tab.
    Reading the whole household is deliberate — a list of names with no
    recipes behind it isn't shoppable, you can't tell what a thing is for.

    FULL, which is what makes this backward compatible: the records written
    during EXPAND have no role and belong to the two people who own the
    household.
    HOW IT'S ENFORCED, and the shape is worth remembering: households/$code
    ".write" became full-members-only, and the guest's permissions are
    re-granted BENEATH it at state/list, state/stapleNeeds and
    state/updatedAt. A deeper ".write" adds permission where a shallower one
    denied, so denying at $code and re-granting narrowly is what produces
    "everything except these paths is read-only". updatedAt has to be in the
    list because every narrow write carries it; without it a guest's write
    would be half-refused and the other phone would never see the change.

    rewrites its own record on each load, so a guest could simply write
    role: "member" and promote itself. The fix is role immutability — but
    the FIRST attempt put that check in members/$uid ".write", where it
    silently did nothing for the people it mattered least about and
    everything for the people it mattered most about... backwards: the
    $code-level ".write" grants a FULL member everything beneath it, and a
    deeper ".write" can only ADD permission, never take it back. So the
    check constrained guests and strangers but did not apply to full members
    at all. It lives in ".validate" now, the only rule kind that always
    runs. A second test caught the corollary: ".validate" doesn't run on
    deletes, which is what lets a guest still leave.
    A knock-on: the membership refresh had to move from set() to update(),
    because a set() that drops `role` reads as CHANGING it and is refused.

THE PARSER (item 40, first half) is done, and the rule that took two attempts
is where a comma is a note and where it is a list. "1 large onion, diced" is a

    item 52's report — "it happened after checking off a bunch of stuff, then

    `.` `#` `$` `[` `]` in a key, so state/list/extras/dr. pepper made the
    Firebase SDK throw before the write ever left the phone:

    `$` `[` `]` throw; `%` and `&` are accepted, so "Milk 2%" and "Ben &
    Jerry's" were never the problem. `/` IS WORSE THAN REFUSED: it is
    accepted, and "1/2 gallon milk" silently writes a node "1" containing
    "2 gallon milk". No error, wrong data.

    IT IS PERMANENT, AND THAT IS THE PART THAT MATTERS. A failed write keeps
    its baseline on purpose (item 21) so nothing is dropped from a future
    diff — so the bad path is re-sent on EVERY write from then on. The error
    never clears, and reopening the app does not help: the key is in the
    device's cached state. That is the shape of the report exactly — it does
    not matter which tap first created the key, only that nothing afterwards
    could succeed.

    NEVER RECEIVED these keys — the write failed every time — so there is no

68. [DONE] AN INVITE TOOK TWO TAPS TO COPY. Reported from real use: "Invite
    another phone" / "Guest link" made the link, but getting it onto the
    clipboard needed a second tap on "Copy link" underneath.

    THAT SECOND TAP WAS NOT LAZINESS IN THE ORIGINAL CODE — it was the fix
    for a real bug (item 48-adjacent): calling the clipboard right after
    `await createInvite(...)` got the write refused on Safari every time,
    because Safari drops the user-gesture context across an await, and a
    clipboard write outside a gesture is exactly what the browser exists to
    block. The link was shown instead, with its own Copy button, because
    THAT tap is a fresh gesture.

    THE ACTUAL FIX ISN'T TO WAIT LESS, IT'S TO NOT NEED TO. createInvite
    picks its own random token (newInviteToken(), a pure function, no
    network) before it ever touches the database — so nothing stops the
    caller from picking that token FIRST. makeInvite (SettingsTab.jsx) now
    does exactly that: mints the token, builds the link, and calls
    `navigator.clipboard.writeText` as the very first thing in the click
    handler — zero awaits before it, so the gesture is still live. THEN it
    calls createInvite with that exact token (sync.js's createInvite grew an
    optional `token` option for this — write it as given instead of minting
    a different one), so the database ends up storing precisely the link
    that's already on the clipboard, not a description of it.
    If that write fails, the existing error path fires exactly as before —
    a copied link nobody can redeem is still worse than no copy, so the
    failure message stays load-bearing, not decorative. If the automatic
    copy itself was blocked, the link still renders with its own Copy
    button, same fallback as always.
    The flash moved from a small word next to the buttons to the panel's
    heading ("✓ Copied to clipboard") — it needed to be the first thing
    read, since the whole point is that there's nothing left to click
    before the link is already usable.

    NOT VERIFIED IN A BROWSER, and said plainly rather than implied: this
    entire flow lives behind `user && !accessDenied && !isGuest`, and `user`
    can only ever be non-null through real Firebase Auth — there is no

    always null there regardless of harness tricks. invitelink.spec.mjs

    the same gap on the creating side. Unit tests, lint and a production
    build all pass, and the change was reviewed by hand against exactly the
    failure mode item 48's comment described — but nobody has watched it
    copy a real link on a real phone. Worth doing by hand before trusting it
    fully, especially on Safari/iOS, which is where the original bug lived.

69. [DONE] KEEP THE SCREEN ON WHILE COOKING. Requested from real use: reading
    a recipe with flour on your hands, the phone locks itself mid-step.

    src/wakeLock.js is a new, small SINGLETON module — not per-component
    state. The screen has exactly one on/off state, and a main's recipe plus
    its sides can each have a RecipeDetail panel mounted, so per-instance
    state would mean the last one you opened deciding the phone's screen
    behaviour, silently overriding whichever one you actually turned it on
    from. One sentinel, one 30-minute timer, one `intentOn` flag every open

    button (📱) next to the ingredients heading.

    currently holds the lock: mobile browsers release a wake lock whenever
    the page is hidden — screen off, a glance at a text, switching apps —

    survive. A `visibilitychange` listener reacquires automatically on
    return, as long as the 30-minute window from the original tap hasn't
    run out; past it, it turns itself off rather than silently holding the
    screen on forever.
    Hidden rather than shown-disabled when `navigator.wakeLock` doesn't
    exist — same rule the guest-only buttons already follow.

    process, set up on first use and torn down once at the end of the file.
    MEASURED, both ends: 205.9s before, 154.7s after, same 194/194. That is
    51 seconds (25%) off every run, and off every CI deploy.

    WHY A CONTEXT IS THE RIGHT ISOLATION BOUNDARY, and how that was checked
    rather than assumed. A context has its own localStorage, cookies and
    cache, and localStorage is the entire state this app persists. Proved
    it directly before switching: wrote a key in one context, opened a
    second context on the same URL, confirmed it could not see the key or
    the cookie. Then proved the SUITE would notice if that stopped being
    true — the mutation test for this change is "make every test share one
    context", which fails 4 of week.spec's 10 tests. Isolation here is
    load-bearing and is actually protected, not merely believed.
    Also instrumented a real run to confirm the reuse happens rather than
    inferring it from the clock: week.spec.mjs now reports 1 browser launch
    and 10 contexts, where it used to be 10 launches.

    ONE BROWSER PER FILE, NOT PER SUITE, and that is the ceiling worth
    taking. `node --test` runs each spec file in its own child process, so
    31 files means 31 launches — down from 194. Going further needs
    launchServer plus child processes connecting over a websocket, which
    swaps a pipe for a socket on every single Playwright call; the cost
    here is startup, not per-call chatter, so that trade is the wrong way
    round.

    TWO THINGS THAT HAD TO BE DONE A PARTICULAR WAY, both found by probing:
      - THE TEARDOWN HOOK IS TOP-LEVEL. Registering `after()` lazily inside
        openApp reads better and is wrong: it attaches to whatever test is
        running at the time, not to the file, so the browser closes after
        the FIRST test. A probe of the lazy version did exactly that.
      - serveDist MOVED TO tests/e2e/server.mjs. harness.mjs now imports
        node:test for that hook, and importing node:test makes a process
        emit its own TAP report — including run.mjs, which is not a test
        process and only ever wanted the file server. The split keeps the
        runner's output clean and draws a boundary worth having anyway:
        the thing that serves files vs. the thing that drives a browser.

    NOT CHANGED, and the obvious next thing if this needs to get faster
    again: the specs are full of fixed `page.waitForTimeout(350-500)`
    sleeps, which now dominate the remaining 154s. Replacing them with
    waits on real conditions would cut more, but it touches every spec and
    trades a slow suite for a possibly flaky one, so it wants its own pass
    and its own evidence.

    ONE ERGONOMIC COST, worth knowing before it wastes an hour: an ad-hoc
    script that imports harness.mjs OUTSIDE `node --test` now hangs at
    exit, because the teardown hook is a node:test hook and never fires, so
    the browser is never closed. Throwaway probes either run under
    `node --test` or close the browser themselves.

86. [DONE] THE TWO PLACES THIS DIVERGED FROM HOW OTHER APPS DO IT.
    Asked after the household design was written up: "would this be how
    other apps handle data?" Mostly yes — access by membership record rather
    than by knowing an id, invites that expire and carry their role, a
    per-user index because RTDB has no query for it. Two things were not,
    and the answer was to remove both rather than defend them.

    A. DELETING THE DATA WITH THE LAST MEMBER OUT (item 17) IS NOT WHAT
       ANYONE ELSE DOES. Slack keeps the workspace, Notion keeps the
       teamspace, Drive keeps the file. The norm is a soft delete: mark it,
       purge after a grace period, allow a restore in between. This deleted
       on the spot, irrecoverably, with two dialogs and Export as the only
       undo.

       THE SAFETY PROPERTY NEVER CAME FROM THE DATA BEING GONE, which is
       what makes the softer version cost nothing. Reading takes a
       membership record and an emptied household has none. What leaked was
       that an emptied household could be CLAIMED by whoever still had the
       code, and claiming it made the list and the recipes readable again.
       So the fix is one clause: a household carrying `deletedAt` can never
       be claimed. The data is then unreachable by every account in
       existence — including the person who deleted it — while remaining
       exactly where it was.

       ONE ATOMIC update(), not two writes: stamp `deletedAt`/`deletedBy`
       and drop the last member together. Split, a failure between them
       leaves a household emptied but unstamped, which is precisely the
       orphan this is trying to stop making.

       RESTORE IS AN UNDO, NOT A SECOND FRONT DOOR. Keyed on `deletedBy`,
       which only ever gets written by an account deleting the household it
       was the last member of. THE ORDER IS FORCED and mirrors leaving:
       clearing the stamps is a write into the household, which takes a
       membership record, so the membership goes back first and the stamps
       come off second. Both stamps are cleared — a `deletedBy` left
       standing on a live household would be a name that can let itself back
       in after being removed — and the rules require `deletedAt` for the
       restore case to fire at all, so a half-finished restore grants
       nothing. Mutation-tested: dropping that requirement fails exactly the
       stale-deletedBy test.

       THE DIALOGS NOW SAY SOMETHING TRUE. They said "this cannot be
       undone", which after this change is a warning harsher than the facts
       — and a warning that is wrong stops people doing things they can
       safely do. They say the month, and where the undo lives.

    B. NO SERVER-SIDE CODE AT ALL was the cause of most of the amber in the
       write-up: the leave race nobody could close, the cleanup script run
       by hand, and the rules file pasted into a console. Every app this
       shape has a small backend for exactly those three. The answer here is
       GitHub Actions rather than Cloud Functions — no billing plan to
       upgrade, and it reuses code this repo already has.

       THE RULES SHIP FROM CI NOW. This was the weakest link in the whole
       design and it was documented rather than fixed: the tests proved the
       FILE, and nothing proved the console matched it. scripts/
       deploy-rules.mjs PUTs it to the same .settings/rules.json endpoint
       tests/rules/harness.mjs already loads the emulator through — NOT the
       firebase CLI, which routes even a 127.0.0.1 upload through this
       sandbox's proxy and dies before it starts, so it could never be
       rehearsed. The REST path works identically against the emulator and
       production, which is the whole reason the deploy is testable at all.
       It compares the PARSED rules, not the text: the server reformats what
       it stores, so a text comparison would report a difference on every
       run and make --check permanently red and permanently ignored.

       THE SWEEP RUNS WEEKLY, and what it may do is deliberately narrow. It
       erases households deleted more than 30 days ago — finishing a job a
       person started. It reports, and does not touch, member-less
       households with NO deletion stamp: nobody asked for those to go, and
       a scheduled job that deletes data nobody asked it to is a worse
       problem than the data sitting there. Clearing those is
       --include-orphans, by hand.

       WHICH ALSO ANSWERS THE LEAVE RACE, without a transaction. Two members
       leaving in the same instant still both see the other and both remove
       only themselves; the orphan that leaves is now found and named every
       Monday instead of accumulating unseen.

    TESTED, and this is the part that changed most. tests/rules/
    sweep.test.mjs drives BOTH scripts as real child processes against the
    real emulator — the sweep's job is end-to-end (read, decide, delete) and
    is only worth trusting if the thing under test is the file the workflow
    runs. Eleven tests, including the two that would matter most: a
    household inside its grace period survives, and a household with members
    survives every flag at once (--delete --include-orphans --grace-days=0).
    MUTATION-TESTED FOUR TIMES: ignoring the grace period fails 3, sweeping
    orphans unasked fails 1, dropping the claim guard from the rules fails
    2, dropping deletedAt from the restore case fails 1.

    AND THEN VERIFIED LIVE, on the real database, the same day — the part
    the tests structurally cannot reach, because leaving and restoring both
    need a database the browser build compiles out. What actually happened,
    in order, on the account that had been collecting junk households since
    item 81:
      - seven households, six of them junk. WORTH RECORDING WHY THE SWEEP
        COULD NOT HELP: it collects households with NO members, and every
        one of the six carried a membership record — that is precisely what
        the churn bug did. They were never orphans. The advice to "run the
        script to clear the junk" was wrong for the case it was given for.
        They were cleared the way a person would: switch to each, leave it.
      - the leave stamped all six. A dry-run sweep then reported exactly
        `6 within grace, 0 orphans` and `nothing to erase`, with the one
        real household untouched. The classification is right about real
        data, not just about fixtures.
      - RESTORE PUT ONE BACK, into the list of households the account is in.
        That closes the last unproven step: membership record back first,
        stamps cleared second, against production rules.
    So the whole path — delete, classify, restore — has now run once end to
    end outside the emulator.

    ONE TRAP FOUND WHILE WIRING IT UP: `node --test` runs each FILE in its
    own process, in parallel, and both rules suites start an emulator on the
    same port. The second one loses — by hanging for sixty seconds and then
    blaming the rules. --test-concurrency=1, said in the file next to the
    port rather than in a commit message.

    AND ONE WORKFLOW SHAPE THAT LOOKS RIGHT AND IS NOT: a step's own `env:`
    is not visible to its own `if:`, so "deploy the rules only if the secret
    exists" has to decide in a step of its own and carry the answer out as
    an output.

    STILL NOT REMOVED, deliberately: the third divergence — minting a real
    household code on load and not using it — turned out to already be
    closed in substance by items 84 and 85. The code is a local document
    identity that gets promoted at first sync, which is the idiomatic
    pattern. Renaming it would be cosmetics.

84. [DONE] EVERY FRESH BROWSER MINTED AND CLAIMED A HOUSEHOLD. Reported after
    item 83 shipped, and worth reading as the end of a run of four: "on the
    side, again having a throwaway household and the main one."

    THE LEAVE PATH WAS NEVER THE ONLY SOURCE. Items 17, 81, 82 and 83 each
    found one way an orphan household got made and closed it, and orphans
    kept appearing. The remaining source was the plainest one in the file:
    App.jsx line 99 mints a code on EVERY load with nothing cached
    (loadDeviceCode), and the membership effect claimed whatever code the
    device happened to be on the instant an account signed in. So every
    incognito window, every reinstall, every browser on a new phone created
    a household and put the account's name on it — before the person had
    chosen anything at all. Nothing about it involved leaving, invites or
    links, which is why fixing those three never made it stop.

    THE FIX IS A DISTINCTION THE CODE DIDN'T HAVE: a code this device
    INVENTED versus a household this device CHOSE. `onboarded` already
    marks the second — it is set by "Start my own list", by joining, and
    now by switching in Settings, and it is true for anyone with cached
    data — so the claim is gated on it. Before that point the code is a
    placeholder.

    AND SIGNING IN NOW ADOPTS WHAT THE ACCOUNT ALREADY HAS. Gating alone
    would leave a reinstall sitting in an empty household with the real one
    nowhere in sight. The users/{uid}/households index (item 80) already
    knows the answer, so an uncommitted device that signs in switches to the
    account's most recently used household instead of the code it invented
    seconds earlier. LIMITED BY WHAT THE INDEX KNOWS — it only started being
    written in item 80, so a household nobody has opened since then is not
    in it yet. It fills in as each one is used.

    THE THIRD STATE IS WHAT MAKES IT CORRECT, and it is the part that was
    missing on the first pass. subscribeMyHouseholds reported {} both while
    it was still loading and when the account genuinely had no households —
    and those want opposite decisions. It reports null until the first
    snapshot now: null waits, {} commits to the device's own code (a new
    account's first household, the path signing in from the first-run screen
    has always taken), and a non-empty index adopts. Getting that wrong is
    not cosmetic: the household rules require a membership record, so a
    device that never commits opens, looks entirely normal, and syncs
    precisely nothing.

    COVERED, FINALLY, BY A TEST — and it took USER_PREVIEW_KEY (item 82) to
    be possible. "Signing in on a brand-new browser commits the device to a
    household" asserts the flag the decision writes, and MUTATION-TESTED:
    dropping finishOnboarding() from the empty-index path fails exactly that
    test and nothing else. What is still NOT covered, said plainly: the
    adoption branch itself needs a real database to have an index to read,
    and this build compiles sync out. The waiting and the committing are
    tested; choosing the right household to adopt is reasoned, not proven.
    207 e2e, `npm run check` green.

    ONE UNRELATED BUILD WARNING FIXED IN PASSING: PantryTab's store <select>

83. [DONE] LEAVING A SPARE HOUSEHOLD MADE ANOTHER ONE, and the join field
    still looked like a code box. Both reported from the same session.

    A. LEAVING MUST GO SOMEWHERE YOU ALREADY ARE. My own design flaw, not a
       regression: leaveHousehold always minted a fresh household, on the
       reasoning that "the device has to land somewhere". That was true when
       an account could only be in one. The moment it can be in several —
       which is now, and which item 80's list exists to show — it is wrong:
       leaving the spare left you holding the real one PLUS a brand-new

       "I tried leaving that household so that I would only have one and
       then it just made a new one."
       Worse, every attempt to tidy up minted another household, which is
       the same orphan churn items 17 and 81 were about.

       is still in, and only mints a code when there is genuinely nowhere to
       land. The local reset stays either way — emptyLocal carries no

       than being overwritten by the one you just walked out of. That
       ordering is the same trap as item 79's, and the reason the reset
       cannot simply be dropped when switching.
       THE DIALOGS NOW NAME WHERE YOU LAND. "A fresh household of its own"
       was a promise that quietly stopped being true the moment you were in

       The label now leads with the link ("Paste the invite link someone

82. [DONE] FOLLOWING AN INVITE LINK AND SIGNING IN PUT YOU IN A DIFFERENT
    HOUSEHOLD — and the fix finally came with a way to TEST this half of the
    app, which is the more important half of the entry.

    THE BUG. The first-run screen was rendered on `!onboarded && authReady &&
    !user`. Signed OUT only. So signing in — the exact thing the invite card
    tells you to do first — unmounted the screen holding the invite and
    dropped you into the app on the code this device had minted for itself.
    Then the membership effect claimed THAT code for the account. Net result:
    the invite was never redeemed, and the account owned a household nobody
    asked for (home-cz6vku5n in the report).
    It also made my own copy from item 70 a lie: "Sign in below, then come
    back to this screen to accept it" — there was nothing to come back to.

    THE FIX. An unredeemed link invite keeps the screen up through sign-in
    (`!user || linkInvite`), and the membership effect does not claim the
    device's own household while one is pending. `linkInvite` gained a setter
    so redeeming or skipping clears it, which is what lets the screen close.

    THE SEAM, and this is the part worth keeping: USER_PREVIEW_KEY, a faked
    signed-in identity that only a local-only build reads — the same shape
    and the same safety rule as GUEST_PREVIEW_KEY. Three reported bugs in a
    row lived behind `user`, unreachable by any test, because a real user
    only exists behind real Firebase Auth. Faking the IDENTITY is enough to
    reach the wiring; access is still decided by the rules, which are tested
    separately against the real emulator, so this seam cannot make anything
    look safer than it is.

    IT PAID FOR ITSELF INSIDE ONE CHANGE. The first version of this fix
    CRASHED the app to the error boundary on any #join link: `invitePending`
    read `onboarded` from the temporal dead zone, and `!!linkInvite &&`
    short-circuits, so the reference is only evaluated when an invite is
    actually present. Every path without a link looked perfect. The browser
    found it in one run; reading the diff would not have.

    MUTATION-TESTED by putting the old `!user` gate back: exactly the two new
    tests fail. Three tests now cover it — the screen survives sign-in with
    an invite, a plain sign-in still goes straight into the app, and "start
    my own list" can still close it so nobody is trapped.

    ONE HARNESS CHANGE CAME WITH IT: openApp's expectFirstRun now mirrors the
    app's own condition. A harness that disagrees with the app about which
    screen is coming does not fail usefully — it hangs for fifteen seconds
    and blames the test.

    WHEN IT BROKE: #81 (85a2229, 2026-08-09) — the change that CREATED the
    first-run screen, so this path never worked. It went unnoticed because
    the screen only appears for a browser with no household data: inviting a
    phone that had already used the app skipped it entirely, and until #101
    two days later the clipboard held a bare invite that pasted cleanly into
    Settings. That combination worked, which is why invites are remembered
    as working. The failing case is specifically a NEW browser following a
    LINK — and both halves of it were introduced by different changes, on
    different days, neither of which could see the other.

81. [DONE] PASTING AN INVITE LINK JOINED A HOUSEHOLD NAMED AFTER THE URL.
    Reported from two browsers: invite from one, copy the link, paste it in
    the other — "it asks to join the household but it is a household that
    isn't the same code", and the account never appeared in the first
    browser's member list.

    IT WAS TWO FAULTS STACKED, and only together did they produce a silent
    wrong success:

    1. THE CLIENT PARSED THE WHOLE URL AS AN INVITE. Since item 48 an invite
       IS a URL, and the field's label says "Paste an invite", so pasting the
       link is the obvious action rather than a misuse. classifyJoinInput
       saw the `~` in it, handed the lot to parseInvite, and parseInvite took
       everything before the `~` as the code — cleanCode strips punctuation,
       so the code became
           httpsstuart-belckegithubiogrocery-runjoi
       Exactly 40 characters of [a-z0-9-], which is a PERFECTLY LEGAL code
       (the rules allow 8-40). Nothing downstream had reason to object.
       FIXED by unwrapping a pasted link first, with parseJoinHash — which
       already existed, and is what a TAPPED link goes through. One
       definition of "pull the invite out of a link", not a second that can
       drift from it. It returns "" for anything that isn't a link, so a
       bare invite or code is untouched.

    2. THE RULES LET THAT SUCCEED. A member record naming an invite, for a
       household with no members, satisfied the FIRST-CLAIM case — so the
       join did not fail, it created a junk household named after the URL
       and made the account its owner. The invite was never redeemed, which
       is why the inviting browser's member list stayed as it was: nobody
       had joined it.
       FIXED by requiring that a first claim carries no `invite` field.
       Presenting an invite has to mean redeeming one: if the record says
       `invite`, the invite case must be the case that passes, or nothing
       does. The client bug is fixed, but a parse mistake should not be able
       to mint households.

    THE PROBE CAME FIRST, BOTH TIMES: the exact pasted URL through the real
    parser (code came back as the mangled URL), and the exact junk record
    against the real emulator (accepted). Then the fixes, then the same two
    checks again. Four unit tests and two rules tests keep them, including
    that a REAL invite still redeems and a REAL first claim still works —
    the guard sits between two paths that both had to keep working.

    WORTH NOTING FOR THE ORPHAN WORK NEXT DOOR: every failed paste like this
    minted a household. Some of the abandoned nodes item 17's script is for
    were made this way, which is also why they are named after a URL.

    WHEN IT BROKE: #101 (ebca4d9, 2026-08-11), "Make an invite an actual
    link" — two days after invites shipped. Before it, Copy put the BARE
    invite on the clipboard (home-xxxxxxxx~token~g), which classifyJoinInput
    has always parsed correctly. #101 changed WHAT GETS COPIED without
    teaching the field that receives it to read the new shape. Nothing was
    broken at the time it was written; the two halves simply stopped
    matching, and no test paired them because the copy path needs a
    signed-in user (item 68's gap) and the paste path was only ever fed
    bare invites.

77. [DONE] A SECOND RULE FOR SCALING INSTRUCTIONS: a number followed by the
    name of an INGREDIENT OF THIS RECIPE. Suggested with the observation
    that makes it safe — an oven is not an ingredient.

    Item 76's unit rule cannot reach "6 whole garlic cloves": `clove` has no
    ratio to anything, so it is not in the unit table and never will be. But
    garlic is in that recipe's list, so the 6 is a count of an ingredient and
    moves with the batch. The recipe's OWN list is the vocabulary, which is
    what bounds the risk: the only words that can trigger a rewrite are the
    words the cook is measuring out.

    MEASURED BEFORE BUILDING, and the measurement changed the design twice.
    Matching only the word immediately after the number caught ONE case in
    the whole catalog, because adjectives get in the way ("6 WHOLE garlic
    cloves", "2 CHOPPED garlic cloves"). Stepping over prep and size
    adjectives caught three, all correct, with no false positives.

    TWO LIMITS, both deliberate:
      - WHOLE INGREDIENT NAMES ONLY, never the separate words of a
        multi-word one. A recipe with "Day-old bread" in it must not make
        "keeps 3 days" scale to 6.
      - PREP AND SIZE ADJECTIVES ONLY are stepped over — no prepositions or
        articles. "for", "to", "of" and "the" would let a number reach
        across to an unrelated noun, and the noun after a temperature is
        very often an ingredient ("reduce to 350 for the chicken").

    ONE REGRESSION CAUGHT BY RE-READING THE CATALOG DIFF, not by the tests:
    widening the word pattern to keep hyphens (needed for ingredient names
    like "sun-dried tomatoes") stopped "15-16 tablespoon-size meatballs"
    from scaling, because "tablespoon-size" no longer resolved as a unit.
    Rule 1 now also tries the stem before the hyphen. Both directions are
    tested.

    THE MUTATION TEST FOUND A TEST THAT PROTECTED NOTHING, which is the
    point of running one. The first version of the whole-names test used
    "Minute rice" against "cook 5 minutes" — and it passed WITH AND WITHOUT
    the bug, because singularish("minutes") is "minut", not "minute", so the
    collision it claimed to test never happened. The mutation (splitting
    names into words) left the suite green. Rewritten with "Day-old bread"
    vs "keeps 3 days", where "days" -> "day" collides for real, and the
    mutation now fails exactly that test.
    ALSO WORTH RECORDING: the first run of that mutation was a no-op — the
    patch did not match the source and silently changed nothing, so the
    green meant nothing either. A mutation has to be PROVEN to have applied
    before its result is evidence; this one is applied by line number and
    the changed lines printed.

    Three mutations, three catches: rule 2 never firing fails 4 tests,
    word-splitting fails the whole-names test, stepping over prepositions
    fails the preposition test. 270 unit, 203 e2e, `npm run check` green.
