Grocery Run — Roadmap
=====================

What is still open. Nine items, none of them urgent — this app does its job.

THE NUMBERS ARE IDs, NOT POSITIONS, AND ARE NEVER REUSED OR REASSIGNED. They
were allocated chronologically, so a low number here means the item is OLD and
still open, not that it matters more. They are referenced from code comments,
commit messages and tests/fixtures/README.md, so renumbering would silently
break every one of those. Items are listed in numeric order because that is
what makes one findable; for what to do next, use the list below.

FINISHED WORK LIVES IN DeveloperNotes-Completed.txt, and most days that is the
more useful of the two: it records WHY the app is the way it is, which is what
you need before changing something that looks odd. Search it before altering
anything surprising, and before redoing anything, too — several entries record
something tried, measured and rejected. A gap in the numbering here means the
item is finished and lives over there.

HOW TO READ AN ENTRY
--------------------

Each says what the thing is, why it has not been done, and WHAT WOULD CHANGE
THE ANSWER. That last part is the point, and it is what to write when adding
one. When you finish an item, MOVE ITS ENTRY to DeveloperNotes-Completed.txt
rather than marking it [DONE] here — leaving them in place is exactly how this
file reached 5,886 lines with ten live items in it.

21. THE READ HALF OF THE DATABASE SEAM.
    The write half shipped: diffPaths computes the narrowest path set, and
    CLAUDE.md carries the rule. The READ half did not. One onValue at
    `state` delivers the WHOLE subtree however deep the write was, so every
    remote change re-normalizes the entire structure and re-renders
    everything.
    DELIBERATELY DEFERRED: it costs nothing at this size, and narrow
    listeners are materially harder than narrow writes — you have to
    reassemble a consistent object from several callbacks that arrive
    separately, which is a new class of bug in exchange for a saving nobody
    can currently measure.
    TRIGGER: a household big enough that a re-render is perceptible, or a
    move off RTDB. Measure before touching it.
    ONE THING WORTH DOING SOONER, cheaply: an ESLint no-restricted-imports
    rule banning `firebase/*` outside sync.js, so the seam cannot regress
    silently. It is currently a convention held by attention alone.

36. SPLIT lib.js WHEN IT MAKES A CHANGE HARD, not on principle.

    Splitting is churn with no behaviour change, and the file has not yet

116. THE RECIPE EDITOR IS A CHOICE OF TWO WAYS IN, NOT A WALL OF FIELDS.
    The owner's reading, and it was right: "the pasting option that most
    people will use is one line above a ton of manual entry fields". The
    card measured 831px at 390 and 937 at 320 — over a full screen — with
    the fast path for most recipes a footnote above the slow one.

    NOW TWO DISCLOSURES: "Start from a recipe or link" and "Recipe
    details", both closed on a NEW recipe. AT REST THE CARD IS 205px, 0.2
    of a screen, and the whole choice is visible at once. Editing an
    EXISTING recipe opens the fields outright — there is nothing to choose,
    you came to change something.

    THE HAND-OFF IS ONE FUNCTION, succeed(), because all three routes in —
    a pasted recipe, a fetched link, a Shortcut import — have to land the
    same way: close the panel that has done its job, open the fields, and
    say what was found. It NAMES AND COUNTS: "Filled in 'Chicken Parmesan'
    — 12 ingredients. Please review it before saving." The count is the
    checkable part; a parse that found two is supposed to look wrong in a
    way that the word "success" never would.

    THAT RETIRED THE OLD NOTE, as the owner predicted. "Fills in the fields
    below from a recipe you copied — or paste a link to one and it's
    fetched for you. Check them before saving" sat above the fields and
    fired BEFORE anything had happened, so it was an instruction to
    remember. The replacement is a result, in the place the thing being
    checked actually is.

    Section (ui.jsx) grew an OPTIONAL controlled mode for this — a parent
    has to be able to close one section and open another, which private
    state cannot express. Existing callers are untouched.

    A keepMounted FLAG WAS BUILT HERE AND THEN DELETED, and the reason is
    worth keeping. The fear was that Section's `{open && children}` would
    discard a half-typed recipe when the fields collapsed. THE MUTATION
    TEST SAID OTHERWISE: it passed with the flag and without it, because
    every field in that form is a CONTROLLED input reading from `draft` in
    MealsTab — unmounting has nothing to lose. The flag was protecting
    against a bug that could not happen. The e2e test stays, because it
    WOULD catch a later refactor that pushed draft state down into the
    section.

    SAVE IS DISABLED WITHOUT A NAME NOW. saveDraft has always returned
    early without one, so the button did nothing when pressed — survivable
    while the fields were open and an empty name box was visibly empty, and
    not once the resting card is a name you cannot see beside a live Save.

    THREE THINGS THE FIRST SCREENSHOT OF THE FINISHED FLOW CAUGHT, none of
    which any check could see — nothing clipped, nothing overflowed, no tap
    target shrank, and every test passed:
    1. THE REMOVE BUTTON WAS ALONE ON ITS OWN LINE. The name's flex basis
       was 120, tuned when the ingredient row was 328px wide; nesting the
       fields in a Section took the row to 294 and the wrap landed one
       control too late. Retuning to 160 moved the defect onto "lb"
       instead. FIXED PROPERLY BY GROUPING: Qty and Unit are now one flex
       item, so a wrap cannot come between them at ANY width — "2 cups" is
       one fact and was always the wrong seam to break on. The row reads
       name + remove, then qty + unit.
    2. EACH INGREDIENT NOW HAS AN OUTLINE, the same paper-and-hairline
       block the Pantry tab uses for a row. Three lines of fields per
       ingredient with nothing between them meant one ingredient's note sat
       against the next one's name and the boundary had to be inferred.
    3. THE ROW OFFERED TO DESTROY ITSELF. "salt and ground black pepper"
       matched the household's "Salt", so a "use 'Salt'" chip sat directly
       beside "split into 'Salt' + 'Black pepper'". One fixes the row; the
       other SILENTLY DROPS THE PEPPER, which is the exact thing the split
       exists to rescue — and both looked like tidy-ups. Suppressed while a
       split is on offer: splitSuggestion knows the name is two
       ingredients, existingIngredientSuggestions does not, so where they
       disagree the better-informed one wins. Mutation-tested.
       THE TEST FOR IT HAD TO BE NARROWED, and the reason is worth keeping:
       "no 'Already have:' anywhere on the page" failed for the wrong
       reason, because the RICE row legitimately offers Brown rice and
       Jasmine rice. The assertion names the two destructive chips instead.

    AN EMPTY NOTE FOLDS AWAY — 147px SAVED ON A SIX-INGREDIENT RECIPE
    (the INGREDIENTS section measured 1128px, now 981). A note that HAS
    something in it still always renders, so the original rule survives
    intact: the parser writes this field, and what it guessed must be
    visible without hunting for it. Only the blank ones go.
    THE FIRST ATTEMPT SAVED FOUR PIXELS. "+ Note" on its own line is 45px
    tall — item 103c's floor says it cannot be shorter — replacing a 45px
    input, so folding the note away bought almost nothing and would have
    shipped as a change that felt like an improvement and measured as
    noise. It only pays once the affordance takes NO line of its own: it
    rides in the Qty/Unit group, and the row drops from three lines to two.
    THE MEASUREMENT IS WHAT CAUGHT THAT, not the screenshot — both versions
    look equally tidy.
    ITS PADDING IS 15px, NOT 13, for the third time in this item: a 13px
    font's line box is 15px, so 13 gives 41 and not 44.

    THE INGREDIENT ROW IS TWO DECLARED LINES NOW, AND THE FOURTH ATTEMPT
    IS THE ONE THAT HOLDS. Three passes tuned a wrapping flex and each one
    stranded a different control at the width it had not been measured at:
    a basis of 120 left the remove button alone at 390; 160 moved that onto
    "lb"; grouping Qty with Unit fixed 390 and left the button alone at 320
    once "+ Note" joined the line. The row is 294px at 390 and only 202 at
    320 once the Section's padding and the ingredient block's are out.

    THE REASON EVERY VERSION FAILED SOMEWHERE: with flexWrap on, AN ITEM
    THAT DOES NOT FIT AT ITS BASIS WRAPS RATHER THAN SHRINKING. At 202px a
    basis of 160 plus the button's 44 plus the 8px gap is 212 — over by

    fill the line it had left. Every "fix" moved the ten pixels somewhere
    else.
    NOW: the Qty/Unit group carries flexBasis 100% so it always starts its
    own line, and the name carries `flex: 1` — basis ZERO, so it cannot
    push anything off and takes exactly what the button does not need.
    Nothing to tune, and identical at both widths: the INGREDIENTS section
    measures 1029px at 390 and 1029 at 320, where it was 981 and 1140.
    390 pays 48px for that; 320 saves 111 and stops being a different
    layout.
    A LAYOUT THAT DIFFERS BY WIDTH IS A LAYOUT WITH A BUG WAITING IN IT —
    every one of these was found by looking at a screenshot, never by a
    check, because nothing clipped, nothing overflowed and no tap target
    ever shrank.

    AN EMPTY NOTE FOLDS BACK WHEN YOU LEAVE IT. Opening "+ Note" and
    changing your mind should cost nothing; without this, every row tapped
    by accident keeps 49px of blank field for the rest of the session and
    the saving above leaks away one mistap at a time. A note with content

    list, so blurring cannot collapse it. Mutation-tested.

    THE ZOOM WAS RECONSIDERED AND KEPT FIXED. The owner's read was that it

    the problem rather than the reassurance: it does not reliably unzoom on

    until you leave the tab or pinch out by hand. It also zooms the PAGE,
    not the field, and the note is the one place you are checking what the
    parser guessed. The deciding argument is the one already in
    screenreader.spec.mjs: a small field put back brings zoom-on-focus with

    maximum-scale=1, which is how pinch-zoom was taken from every Android
    user in the first place.

    THE NOTE FIELD HAS BEEN ZOOMING iOS SINCE THE DAY IT WAS ADDED, and
    the test that exists to prevent exactly that never saw it. Reported as
    "clicking + Note zooms in" — autoFocus made a long-standing bug
    instant and therefore visible. The field was 13px; theme.js is explicit
    that under 16 makes Safari zoom the whole page, and that index.html
    once "fixed" this by banning zoom outright, taking pinch-zoom from
    every Android user permanently.
    WHY screenreader.spec.mjs MISSED IT: it walks the tabs and opens the
    disclosures it knows about, but IT NEVER PRESSED "Add a meal". Every
    field in the recipe editor was therefore unscanned — the assertion was
    real, its reach was not. It opens the editor now, plus both of item
    116's sections and the "+ Note", and mutation-tests red at 13px.
    A TEST THAT CANNOT REACH THE FIELD IS NOT PROTECTING IT, which is the
    same lesson as the placeholder measurement two items up: the editor
    audit reported "0 clipped text" on a form with a placeholder being cut
    off, because it walks text nodes and a placeholder is not one.

    THE PLACEHOLDER LOST AN EXAMPLE TO PAY FOR THE FONT SIZE. 16px text is

    diced)", 143px. The name and the "e.g." are what survive, because they
    are what this placeholder was established to be FOR.
    AND THE PLACEHOLDER HARNESS WAS OVER-REPORTING: it compared a
    TEXTAREA's placeholder against one line of its box, so the paste box
    and the instructions box both read as cut when a textarea placeholder
    WRAPS. Inputs only now.

    SIX e2e SPECS OPEN THESE FIELDS TO TYPE INTO THEM and needed an

115. THE URL IMPORT HAD NO TIMEOUT — FIXED, AND WHY IT WAS INVISIBLE HERE.
    Reported from real use: on the DuckDuckGo browser, pasting a link left
    the panel on "Fetching…" forever. In Chrome the same link answered at
    once — host_not_allowed, juliasalbum.com being off the allowlist — which
    is exactly why the hang never showed up in testing.

    fetchRecipeFromUrl called fetch() with no AbortSignal. fetch REJECTS on
    a refused connection, so the try/catch around it read as complete
    coverage; a request that is STALLED rather than refused never settles at
    all, and nothing was watching a clock. A privacy browser holding an
    unfamiliar third-party domain — workers.dev is precisely that shape —
    produces this, as does a captive portal or a phone losing signal
    mid-flight.

    NOW AbortSignal.timeout(15000), a "timeout" reason of its own, and its
    own message: a refusal might work on a retry, a timeout on this network
    probably will not, so the two must not say the same thing.

    COVERED BY AN e2e TEST THAT REALLY WAITS THE 15 SECONDS — a route left
    un-fulfilled IS the stalled request. Mutation-tested both ways. Stubbing
    the clock would have passed on a build with no timeout at all.

    WHAT WOULD CHANGE THE ANSWER: if the Worker grows a slow path of its own
    — a render step, a retry — 15s stops being generous, and the number
    wants a measurement rather than a guess.

101. MAKING A HOUSEHOLD IS A FIRST-RUN-ONLY ACTION, AND THAT IS NOW ODD.
    Asked while reading Settings: "if you can get invited to multiple, why
    not be able to make new ones?" The asymmetry is real rather than
    intended — left over from when a device had exactly one household.
    Settings can SWITCH between households, RESTORE a deleted one and JOIN
    one by invite, but cannot make one. So an account accumulates households
    only by being invited, which is backwards.
    WHY IT IS NOT A ONE-BUTTON JOB:
      - CLAIMING IS THE DANGEROUS BIT. Items 83, 84 and 85 are three rounds
        of "the app made me a household I did not ask for". A Create button
        re-opens exactly that surface, so it has to be deliberate and
        confirmed, landing you IN the new household rather than quietly
        seeding one.
      - IT NEEDS A NAME AT BIRTH. A second and third household called
        home-xxxxxxxx is unreadable in the switcher.
      - WHAT DOES IT START WITH? Empty, or a copy of the starter catalog?
        Both are defensible and they are different products.
    TRIGGER: a second real household existing to want. Two people, two
    phones, one household today.

102. PER-DEVICE VERSUS PER-HOUSEHOLD SETTINGS, a distinction the app makes
    but never says out loud. Everything under Preferences is the
    HOUSEHOLD'S — units and week start live on the catalog node, decided so
    that two phones cannot disagree about what the plan grid means.
    But the app already has per-device state and does not call it settings:
    the home-screen dismissal, the seen-set of announced households, the
    device's own household code, the caches. None is exposed or labelled as
    belonging to this phone rather than everybody.
    THE QUESTION TO ANSWER FIRST is which side each setting belongs on, and
    UNITS IS THE ARGUABLE ONE — one person reading metric while the other
    reads standard costs nothing, because it changes how a total is
    displayed and not what it means. Week start is not arguable.
    TRIGGER: revisit alongside 101; they are the same conversation.

110. THE PARSER: STOPPED AT GOOD ENOUGH, and the list to resume from.
    Five real pages from five sites parse correctly — every ingredient list,
    every step list, four of five serving counts. tests/fixtures/README.md
    names each one, its URL, and the single rule it taught. That file is the
    per-site detail; this is only what is left.

    STANDING TASK: MORE CAPTURES. The intent is to hand over another batch of
    recipe links when there is time and budget for the testing. Five sites is
    where this stopped for cost reasons, not because the returns had fallen
    off — EVERY page so far broke something the previous ones did not, so
    expect the next batch to as well. Capture them the way the five were
    (Get Contents of URL -> Copy to Clipboard, nothing in between), run each
    through parseRecipeText BEFORE changing anything, and fix what the output
    actually shows.

    WHAT TO PICK UP FIRST, in the order that would teach the most:
      - DONE — THE NAME NOW COMES BACK ON ALL FIVE. It was blank on every
        page, which meant typing the title by hand on every import. Blank was
        deliberate (a blank field asks to be filled in, a wrong one gets
        saved), so replacing it had to be right far more often than wrong.
        NOT A GUESS AT WHAT A TITLE LOOKS LIKE — that is what item 109
        records building, measuring and reverting. A STRUCTURAL fact instead:
        every recipe site puts a "Home > Category > Category" trail directly
        above the page heading, and the heading is the recipe. Two trail
        styles cover all five; AllRecipes uses neither arrow — a bulleted
        all-caps trail spaced out with runs of spaces.
        titleAfterBreadcrumb() in lib.js falls back to blank and never to a
        guess, so it can only improve on the old answer. A paste has no
        breadcrumb — a person starts selecting at the recipe — so pastes are
        untouched. AverieCooks shouts its heading, so an all-caps line is
        sentence-cased through cap(), the same path every ingredient name
        takes.
        STILL OPEN UNDERNEATH IT: a site with no breadcrumb at all has never
        been seen, and would come back blank as before.
      - A UK OR EUROPEAN SITE has never been tested. The parser was taught
        "500g" and "200ml" against MADE-UP lines, never a captured page —
        the same untested-assumption shape that item 109 records going wrong.
      - A PAGE WHOSE STEPS ARE PLAIN PARAGRAPHS, neither bulleted nor
        numbered. All five fixtures bullet or number theirs.
      - PER-COMPONENT INGREDIENT GROUPS beyond the two seen so far. The
        bullet rule that separates them is the newest thing in the file.
      - A BARE NUMBERED LIST WITH NO "INSTRUCTIONS" HEADING is read as more
        ingredients. Found while writing item 106's tests, on a hand-typed
        recipe rather than a captured page — all five fixtures carry the
        heading, which is why none of them caught it. It bites a PASTE of
        something somebody typed themselves, not a fetched page, so it is
        smaller than it looks. tests/e2e/specs/importlink.spec.mjs says so
        where it works around it.
      - DONE, AND THE LESSON IS WORTH MORE THAN THE FIX: "salt and ground
        black pepper" was ONE ingredient, and on the AllRecipes page that
        card ALSO lists "1/2 teaspoon salt" — so salt reached the list under
        two names that cannot be added up.
        THE FIRST ATTEMPT WAS A REGEX IN THE PARSER, splitting on "and" when
        the line says "to taste" — wrong twice over, and item 40 had already
        settled both halves. It INVENTED A SIGNAL THAT EXISTED —
        existingIngredientSuggestions already returns Salt AND Black pepper
        for that row, two known ingredients matching one row, and the
        catalog tells it apart from "4 cloves garlic peeled and cut in
        half" (only "Garlic" resolves) with no marker word needed. And it
        DECIDED INSTEAD OF ASKING, which is the exact failure item 40 exists
        to record.
        NOW: splitSuggestion() in lib.js proposes on the separator and lets
        the catalog confirm both halves, rendering a chip beside the
        "Already have:" one. Accepting returns the CATALOG's names, so it
        unmerges the row and canonicalizes both at once.
        BEFORE REACHING FOR A HEURISTIC HERE, CHECK WHETHER THE CATALOG
        ALREADY KNOWS. It usually does, and the evidence beats the hint.
      - KNOWN WRONG, RARE: "2 x 400g tins", "1 lb 2 oz", "1 tbsp + 1 tsp",
        "Juice of 1 lemon" (arguably already right — the ingredient IS a
        lemon).

    THE RULE THAT MATTERS MORE THAN THE LIST, earned twice in one session:
    A FIXTURE BUILT FROM YOUR OWN UNDERSTANDING CANNOT TEST THAT
    UNDERSTANDING — it can only agree with it. Capture the page, do not tidy
    it, and mutation-test every rule, because a green suite that was going to
    be green anyway is worse than no suite: it feels like evidence.

113. GROWING THE RECIPE-IMPORT ALLOWLIST — SIX ADDED, ONE STILL OPEN.
    Prompted by real use: a juliasalbum.com link was pasted and refused.
    The site was fine; it simply was not on the list.

    PROBED FROM A GITHUB RUNNER, not from Cloudflare's own IPs as the first
    sixteen were. The sandbox this is written in cannot reach recipe sites
    at all — its egress proxy 403s them — and a runner has open internet.
    findRecipeNode was LIFTED OUT OF worker/index.js rather than
    reimplemented, so the probe could not drift from production. The
    fidelity gap that leaves — a site could allow GitHub and block
    Cloudflare — closes for free: deploy-worker.yml already curls the LIVE
    Worker after deploying and greps for "ok":true, so production confirms
    the list on the way in.

    ADDED (7), each serving a Recipe node with a non-empty recipeIngredient:
      juliasalbum.com, loveandlemons.com, halfbakedharvest.com,
      sallysbakingaddiction.com, foodiecrush.com, iowagirleats.com,
      eatyourselfskinny.com.
    Three of the seven came from the owner's OWN catalog. With the four
    walled sites below, that is 27 hosts.

    REFUSED, ALL DOTDASH MEREDITH: eatingwell.com, allrecipes.com,
    simplyrecipes.com, seriouseats.com — HTTP 402 with a 612-byte body, on
    the HOMEPAGE, before any recipe was reached. Consistent with the
    licensing wall already recorded against allrecipes.

    AND THEY ARE ON THE ALLOWLIST ANYWAY, on the owner's call, which is the
    better design. Off the list they got "that site isn't set up for
    automatic import yet" — UNTRUE of them: they are set up, they decline.
    Allowed, the Worker really tries, gets the 402, and says so by name:
    "allrecipes.com blocks automatic import — that is the site's choice,
    not a problem with your link." It also SELF-HEALS; if a wall ever
    lifts, they start working with no code change and no probe.
    A REFUSAL IS NOW A DIFFERENT ANSWER FROM A FAILURE. 401/402/403/406/
    429/451 are a site turning a reader away and will not come good on a
    retry, so they return "site_blocked" with the host; a 404 or a 500 is a
    wrong link or a broken page and stays "fetch_failed". The host travels
    all the way through — Worker, recipeImport.js, into state — and the
    e2e test mutation-fails if any link in that chain drops it, which
    matters because a dropped host degrades silently to "That site" rather
    than throwing.
    THE COST, STATED: one real fetch and one of the day's 20 import slots
    spent on a request that will very likely fail. That is the right trade
    at 20 a day. It would not be at 2.

    A TRUE NEGATIVE: smittenkitchen.com publishes no JSON-LD. 24 real pages
    walked, twice, none carrying a Recipe node — hand-written HTML rather
    than a recipe plugin. Pasting its text still works, as it does for any
    site.

    eatyourselfskinny.com — THE PROBE SAID IT DID NOT WORK, AND THE PROBE
    WAS WRONG. Its crawler found no links (JavaScript homepage) and no
    sitemap at any path it knew, so it reported "no Recipe node on any of 0
    pages", which reads exactly like a refusal. The owner supplied ONE real
    recipe URL and it answered HTTP 200 with 24 ingredients and a
    recipeYield of 8. Added. 27 hosts.
    THIS IS THE CLEAREST CASE OF THE RULE BELOW: a site was one line away
    from being written off on the strength of a bug in the thing testing
    it. The cheapest fix for a "0 pages" result is to ask a person for one
    URL, not to write more crawler.

    THE PROBE WAS WRONG TWICE, AND BOTH TIMES IT LOOKED LIKE A SITE
    REFUSING US. First it guessed recipe slugs and took six 404s; then it
    nested the sitemap array inside itself and reported a host as FAILED
    that had never been asked. WHAT THAT MEANS NEXT TIME: a negative from
    this probe is worth re-reading before it is believed, because every one
    of its own bugs presents as a host that does not work. A POSITIVE needs
    no such doubt — it required a real Recipe node to come back.
