Grocery Run — Roadmap
=====================

A single, prioritized backlog combining the earlier scattered notes with the
newer batch of ideas. Duplicates and closely-related items have been merged.
Tiers are ordered: cheap high-impact UX wins first, then the Ingredients-tab
cluster (which shares a refactor), then data-model changes, then the riskier
multi-device / integration work last. A Hygiene section after Tier 4 collects
the work that isn't a feature — tests, shared logic, and the database seam.


Tier 1 — small, high-value, low-risk
------------------------------------
1. [DONE — #11, #12] Recipe detail view. Tapping a recipe card in the Meals
   tab expands its full ingredients + notes, read-only, without having to hit
   Edit.
2. [DONE — #11] Remove a meal from "the list". After "Add to list" from the
   Meals tab, give an explicit way to take it back off. Also handle meals that
   reached the list via the Week plan, not just the Meals tab.
3. [DONE — #11] Suggested "unit" values when adding a new item.
4. [DONE — #11] Move the settings section off the bottom of the Ingredients
   page into a dedicated Settings tab (or a hamburger menu at the top). Do
   this before adding search/filter to the Ingredients tab so it isn't
   cluttered.
5. [DONE] Checked-off items: gray only the name, not the details. The whole
   List row no longer dims on check — only the item name gets the
   strikethrough + dim, so expanding a checked item keeps its "On the list
   for" breakdown at full opacity and legible.
6. [DONE] Week-plan meal picker. Each day/meal slot is now a tap-to-open
   button (showing the assigned meal, or "＋ Choose a meal") that opens a
   searchable modal mirroring the Meals tab — a search box plus recipes
   grouped "{type} meals" / "Other meals", each showing servings + tags, with
   the current pick checked and a "Remove meal from this slot" option. Replaces
   the native <select> that didn't fit the app's feel or scale with the list.


Tier 2 — Ingredients-tab cluster (shared refactor, then features)
-----------------------------------------------------------------
7. [DONE] Ingredients tab row treatment. Each row now collapses to just the
   ingredient name (with a subtle default-store · aisle hint), a gear, and an
   X. Tapping the gear or the name expands the row to edit the default store
   and per-store aisle numbers; Rename lives inside that expanded panel.
8. [DONE] Make the Ingredients tab filterable by store and A-Z, and add
   search. A search box (name match, with a clear ✕, mirroring the Meals tab)
   plus a store-filter dropdown ("All stores" / each store / Unassigned) that
   narrows to items with that default store. List stays A-Z sorted.
9. [DONE — #17] Ingredient rows show which recipes they're used in (inside
   the expanded gear panel, alongside whether it's also hand-added to the
   list) rather than as a separate info icon.
10. [DONE — #17] Add ingredients to the shopping list straight from the
    Ingredients tab. Each row gets a "+ List" button that becomes a
    ± quantity pill (with a tap-to-type-exact-amount) once it's on the list,
    defaulting to whatever unit recipes most commonly measure it in.
11. [DONE — #17] The List tab's "add an item" field now suggests matching
    known ingredients as you type (name + default store, keyboard-navigable),
    so you pick an existing item instead of creating a duplicate.
12. [PART DONE] Suggest units as you type when adding a new ingredient.
    The CONVERSION half is built; the suggestion half below is still open.

    What shipped: a factor table in lib.js grouping units by dimension, and
    resolveAgainstBought doing the cupboard subtraction in base units so
    buying 1 lb offsets a recipe asking for 16 oz. That was the costly bug —
    the item stayed on the list looking unbought and you bought it twice.
    Amounts that can be added are added (1 lb + 8 oz reads 1.5 lb), and
    commonUnitFor now weighs by dimension so one "can" can't outrank an lb
    and an oz that between them say this is measured by weight.

    Two decisions worth keeping:
      - PROMOTION NEVER CROSSES MEASUREMENT SYSTEMS. Display picks the largest
        unit that keeps the number at or above 1, stepping down when it would
        fall below: 24 oz reads 1.5 lb, 1500 g reads 1.5 kg, a quarter pound
        reads 4 oz. It will promote to a unit nobody typed, because g/kg and
        oz/lb are one scale that everyone reads at a glance. It will NOT cross
        between them — answering "how much flour" in a system this household
        doesn't use is the surprise actually worth avoiding, and that is the
        one thing the metric/standard setting (item 31) would authorise.
        Two carve-outs, both learned by looking at the output:
          pt / qt / gal convert but are never promotion TARGETS. They're
          container sizes; a recipe wanting 2 cups of stock read "1 pt".
          Count units don't promote at all and show in the SMALLEST unit used:
          a dozen eggs plus two more is "14 ea", not "1.17 dozen".
      - US factors are defined from their exact ratios (1 lb = 16 oz, 1 cup =
        16 tbsp, 1 tbsp = 3 tsp) rather than via the metric base, so 16 oz and
        1 lb compare exactly instead of missing by a float hair and leaving
        0.0001 lb on the list.
    An amount with qty 0 ("salt, to taste") is kept at zero rather than
    dropped — an empty group is not the same as a covered one.

    STILL OPEN — the original item: Extend the unit
    suggestions (item 3) to the ingredient-adding flow — the recipe editor's
    add-ingredient row and the Ingredients tab — offering the units already in
    use as you type. Must still let you type a brand-new unit and use it; the
    suggestions never restrict entry to a fixed set.


Tier 3 — data-model / sorting
-----------------------------
13. [DONE] Pantry staples — things you own, kept off the list until you run
    out. `config[key].staple` marks one; `stapleNeeds[key]` says you're out.
    Two decisions that shaped everything after:
      - NO PARALLEL DATA STRUCTURE. A staple is an ordinary ingredient with a
        flag. "The staples list" is only ever a VIEW. Nothing to migrate,
        nothing to keep in sync.
      - THE SPLIT BY LIFETIME, which later features copied: the designation is
        a durable fact about the kitchen and lives in the catalog; being out is
        trip state and lives in the shopping state. Only "need" entries are
        stored, so an all-clear state tidies itself away.
    A staple carries forward if you didn't buy it, rather than needing
    re-entry — that is why it beats a weekly "what are we out of" prompt.

14. [DONE] Once an item is checked on the List, move it to the bottom of its
    group and keep following the A-Z / store-flow sort the user has selected.
15. [DONE] Recipes reference the shared ingredients list to avoid duplicates.
    The recipe editor's ingredient-name field now suggests matching known
    ingredients as you type (name + default-store hint, keyboard-navigable),
    reusing item 11's List-tab pattern, so you pick an existing item's exact
    spelling instead of forking a spelling variant into a separate ingredient
    and shopping-list line. Recipe ingredients still store { name, qty, unit };
    the suggestions steer them onto canonical norm(name) identities.


Tier 4 — multi-device / integrations (highest risk, do last)
------------------------------------------------------------
16. Formalize create/join household. Household codes already exist under the
    hood; this makes creating or joining one a first-class flow.
17. Delete / log out of households, and clean up orphaned data. Households
    created by devices we no longer use linger in the RTDB forever; a device
    with uncommitted changes on a separate household keeps it alive. Figure out
    whether deleting requires logging everyone out (or logging specific
    households out) and how to reclaim abandoned nodes.
18. Export to / link with a Google calendar, keyed off the household.

    Note: 16 and 17 are both patches on top of a catalog that can't be written
    at runtime. Moving the catalog into the database per account replaces them
    instead of extending them, and deletes the whole override layer with it.
    That's written up as a platform phase in FutureProjects.md ("Per-user
    catalog") — worth reading before starting either item.


Hygiene — not features, and not sequenced
------------------------------------------
None of these ship anything on their own. They're what keeps the app cheap to
change: a test layer, one place for shared logic, and a database seam narrow
enough to swap what sits behind it. Do them alongside whatever feature is next
rather than saving them for a cleanup that never gets scheduled.

19. [DONE] Tests on the pure layer. `npm test` runs node's built-in runner
    over lib.js — 100+ tests, no framework installed. CI runs lint, tests and
    build before deploying, in that order, so a failure stops the deploy rather
    than annotating one that already shipped.
    MUTATION-TEST ANYTHING LOAD-BEARING: break the rule deliberately, confirm
    the right tests fail, restore. A test that passes either way protects
    nothing, and several here originally did.

20. [DONE] Make a failed write visible. A rejected write used to be
    console.error and nothing else — invisible on a phone, where there is no
    console. Both writeHousehold and writeCatalog now report through a small
    pub-sub in sync.js (watchWriteErrors), which App.jsx subscribes to and
    reuses the SAME dot/label the offline state already draws with — no new
    visual language, just a truthful reason attached to the existing one.
    Offline is deliberately NOT this: the SDK queues writes in memory and
    flushes on reconnect without ever rejecting, so the signal only fires when
    the server actively refuses a write while connected (rules, quota, a
    malformed payload). Self-correcting, same shape as the update gate: it
    clears the moment any write succeeds again, no dismiss button needed.
    Done together with item 33 — same file, same theme, and fixing 33 first
    made 20 land on writes that no longer intermittently reordered anyway.

21. Keep the database seam narrow. Every database call lives in sync.js, and
    App.jsx is the only component that touches sync at all (SettingsTab
    imports syncEnabled, and nothing else — cleanCode moved to lib.js when
    parseInvite needed the same alphabet, which narrowed this further; the
    invite and member calls it needs arrive as props). That
    property, not any clever abstraction, is why RTDB could be swapped for
    Firestore in days rather than weeks. Defend it deliberately as usage
    grows and the right database stops being obvious:
      - no `firebase/*` import outside sync.js. Add an ESLint
        no-restricted-imports rule so it can't regress silently.
      - the seam should say WHAT CHANGED, not hand over everything.
        toggleChecked(key, on), not writeHousehold(entireState). RTDB
        implements that as a write at one path; Firestore as a document
        update. Neither is forced into the other's shape.
      - this also retires the update() footgun. Two update() calls in one
        handler discard the first, because both rebuild from the same stale
        snapshot — that is what broke the staple checkbox, and a comment on
        the function is not enforcement. Narrow writes remove the constraint
        instead of documenting it.
      - do NOT abstract queries or offline storage. Those genuinely differ
        between the two databases and a wrapper inherits the weaknesses of
        both. Keep filtering in JavaScript, and keep loadCache/saveCache as
        thin as they are — a Firestore migration deletes them outright rather
        than porting them.

    THE READ HALF IS STILL OPEN, AND IS DELIBERATELY DEFERRED. Narrow writes
    shipped; narrow listeners did not. One onValue at `state` delivers the
    WHOLE subtree however deep the write was, so every remote change
    re-normalizes the entire structure and re-renders everything.
    DO NOT DO THIS YET. Item 25's measurement killed the case for doing it now:
    the whole synced node is 954 BYTES, so the widest possible listener
    delivers under a kilobyte, and re-normalizing that plus a re-render is not
    worth a refactor that breaks four things (below).
    THE CATALOG MOVE WAS PREDICTED TO BE THE TRIGGER, AND IT WASN'T. This entry
    used to say the move would take the listened-to node from ~1 KB to ~30 KB
    and finally make the four costs worth paying — "do it immediately after
    that move, not before". The move shipped and that never happened, because
    the growth landed on its OWN node (households/{code}/catalog) rather than
    inside `state`. The listener at `state` still delivers about a kilobyte.
    The move made this case WEAKER, not stronger; item 37's "what's left"
    records the same conclusion from the other direction.
    THE REAL TRIGGER IS MEASURABLE, NOT ARCHITECTURAL: `state` itself getting
    big — per-person data, trip history, anything that stops it being one
    shared list — or re-render jank someone can actually feel on a phone.
    Re-measure with item 25's method before acting on it. Predicting this one
    by reasoning about the architecture is exactly what just went wrong.
    What it costs, so it isn't a surprise:
      - the atomic snapshot. Branches start arriving independently and out of
        order instead of as one coherent state.
      - pickState as written. It compares ONE updatedAt for the whole blob to
        decide local-vs-remote at launch; per-branch updates need per-branch
        stamps or a different staleness rule.
      - "is this a new household?", which today is just remote === null at the
        state node and drives the seeding path.
      - normalizeLocal splits into per-branch normalizers. That is where it
        should end up anyway, but it is work.
    Related measurement in item 25 — informative, not a gate.
    Background in FutureProjects.md ("Per-user catalog").

    UPDATE, once the catalog move shipped: the catalog went to its OWN node
    (households/{code}/catalog) with its OWN listener and its OWN updatedAt,
    not into the state node. So the ~30x growth this item was waiting for
    never lands on `state` — it lands next to it, already split. Ticking a
    checkbox still delivers under a kilobyte, and editing a recipe delivers
    the catalog without touching the list.
    That is one branch of the per-branch split this item describes, done for
    the branch that actually needed it, and it cost none of the four things
    above: each node keeps its atomic snapshot, keeps a single updatedAt that
    pickState reads unchanged, and keeps "remote === null means seed me".
    What remains open is splitting the STATE node itself (list vs plan vs
    stapleNeeds), and the case for that is still weak at 954 bytes. The next
    real trigger would be a third party in the household, not size.

    The adopt-vs-push rule is now shared. Both nodes route their listener
    through the same pickState: newer stamp wins, ties go to remote so two
    phones don't bounce a value between them, and no remote at all means
    seed. The catalog needed it for a specific reason — updateCatalog can't
    write before the listener has reported (writing early could replace a real
    catalog with a locally seeded copy), so an edit made offline sits on disk
    unwritten, and adopting on connect would silently discard it. A pristine
    seed carries updatedAt 0 precisely so it can never win that comparison;
    only an actual edit stamps a real time.

22. [DONE] List-building logic moved out of the tabs into lib.js. The tabs
    were 600-750 lines each, mixing data logic with rendering, and none of it
    was testable. Everything with a rule in it — aggregation, filtering,
    sectioning, unit conversion, ingredient identity — now lives in lib.js and

23. [DONE] Ingredients have a stable id. The key used to BE the name, so
    renaming orphaned every reference — and two were already being lost in
    practice, because list.bought and stapleNeeds were added after the rename
    code was written and nobody went back.
      ingredients: { ing_7f3a2b: { name, store, aisles, staple } }
      recipe lines: { ingredientId, qty, unit }
    THE FILE STAYS NAME-KEYED. catalog.json is hand-edited and diffed in git;
    ids in it would mean inventing one and matching it across two sections just
    to add a recipe. Minted on the way in, resolved back to names on export.
    THE TRICK THAT KEPT IT SMALL: App resolves each line's id to a name when it
    assembles `data`, so every tab that reads i.name was untouched.
    Reads still accept a legacy norm(name) reference — expand phase. THE
    CONTRACT PHASE IS STILL TO DO: drop that fallback once both phones have run
    the migration and been used for a few days.
    The migration fires from the catalog LISTENER, never at startup. Converting
    offline would let a device mint ids, remap its state onto them, then adopt
    the other phone's catalog with DIFFERENT ids and orphan everything. Exactly
    one authority converts.

    TWO BUGS FOUND BY USING IT, NOT BY TESTS — both "code written when the key
    WAS the name":
      1. Four places read a key and treated it as a name. Two rendered
         "Ing_c45b0s82" where a name belonged; worse, the Ingredients add box
         and the recipe editor WROTE name-keyed entries into an id-keyed
         catalog, which would have reintroduced the old shape one entry at a
         time while looking fine. Everything that turns a typed name into an
         ingredient now goes through ensureIngredientId; everything that
         displays one uses ingredientNameFor.
      2. Renaming onto an existing name created a DUPLICATE. Impossible while
         the key was the name, and the old rename merged instead — a rule
         dropped along with the key-moving it needed. Renaming now merges,
         repoints recipes, sums a line that would otherwise duplicate, and asks
         first because a merge deletes an ingredient.
    THE LESSON: the migration was correct both times. What broke was ordinary
    EDITING afterwards. A migration test that only checks the conversion misses
    this entire class.

24. [DONE] Concurrently-edited collections are keyed by identity, not arrays.
    An array index is not a stable identity: two phones appending at once
    collide, and neither database can address one element without rewriting the
    whole list. diffPaths treats arrays as ATOMIC for that reason, so a keyed
    object is what makes a narrow write possible at all.
    Stores stay an array deliberately — order is meaningful (it drives
    store-flow grouping) and they're edited about never.
    Accepting the legacy shape on read is permanent, not transitional: Firebase
    hands arrays back as index-keyed objects regardless.

    was 954 BYTES, not the ~30 KB assumed, because the catalog wasn't in it.

    Done AFTER the catalog move, deliberately — it changes the shape of a plan

28. [DONE] Meals that don't feed the shopping list — leftovers, or a meal
    you're already stocked for. `skipList: true` on the slot, surfaced as

    The label names the EFFECT, not one reason for it. Two list-facing walks
    honour it through one shared `slotFeedsList`; plannedMealCount deliberately

    Unticking DELETES the key rather than storing false, so a plan that never

29. [DONE] Sticky controls, via a shared <StickyBar> in ui.jsx, on Meals,
    Ingredients and List. Invisible at rest; hairline and shadow only while
    actually stuck, read from a sentinel through IntersectionObserver rather
    than a scroll handler.
    WHAT TO PIN IS THE DESIGN, and it differs per tab: pin what you reach for
    WHILE scrolling, not everything that lives at the top. Pinning the whole
    List header came to three wrapped lines at 390px, so "Done shopping" and
    the meal count stayed below.
    A sticky ancestor with a z-index creates a stacking context — the Filter
    popover had to be checked with elementFromPoint, not by eye. The bar also
    cancels the page's 14px side padding, or rows show through at the edges.

30. Warn when another device is running an older build. Two phones on the same
    household diverged this week, and the only signal either gave was "Synced",
    which means the socket is connected and nothing about whose data won. Stamp
    each write with the build id already shown in Settings, and let a newer
    build say "another device is on an older version" when it sees an older
    stamp. An old build can't warn about itself — but the new one can warn
    about it, which is enough. TIER 4.

    Prerequisite, now done: the stamp has to name a commit that exists. On a
    pull request Actions checks out a temporary MERGE commit, so every preview
    was stamped with a SHA found nowhere in the branch. That cost a real
    debugging session during the catalog move — a phone was serving a stale
    preview and the only way to tell which build it had was matching its
    timestamp against gh-pages deploy times. CI now passes the pull request's
    head SHA through as BUILD_SHA and vite.config.js prefers it. Stamping
    writes with an id nobody can look up would have made this item worse than
    useless, so it had to be fixed first.

    Context, because it looked worse than it was: neither phone was old enough
    to do whole-state writes. The likely cause was #39's migration, which makes
    each device do ONE full set() the first time it writes after updating, to
    replace the old array shape. Both phones did that at about the same time
    and one overwrote the other. Known and accepted at merge time, spent once
    per device, and not recurring — but it took reading build stamps off two
    phones to establish that, which is what this item is for.

31. [DONE] Preferences: units (as-entered / metric / standard) and week start,
    in a Settings tab where every section is now tap-to-open.
    HOUSEHOLD, NOT DEVICE — they live on the catalog node. Two phones
    disagreeing about the week start would make the plan grid mean different
    things on each, which is worse than either answer.
    Display only; nothing is rewritten, so either can be flipped back freely.
    The units preference is what AUTHORISES crossing measurement systems, which
    item 12's conversion layer refuses to do unprompted. It also can't strand a
    total: counts and invented units have no metric form, so choosing one
    leaves them alone rather than dropping them.
    The week start ROTATES the presentation order and never renumbers: plan
    data is keyed by day name. Only WeekTab needs it — the aggregation walks
    DAYS to sum, and a sum doesn't care about order.
    Defaults are Sunday and standard. Note the trap that exposed: a default
    written as `x === "Sun" ? "Sun" : DEFAULT` silently makes the OTHER value
    unselectable once the default flips. Whitelist, don't compare.

32. [DONE] Update detection and the write gate.
    TWO MECHANISMS, KEPT SEPARATE, and that separation is the point:
      SOFT — the site is serving a different build. A modal offering Reload,
        dismissible per build. Right for almost every release.
      HARD — the household's catalog was written by a NEWER generation. Writes
        refused, reads untouched. A shopping list you can't open in a shop is
        worse than one you can't tick items off in.
    Both are modals, not banners: a banner at the top of a scrolling page is
    exactly what gets scrolled past. The gate keeps a banner TOO, so dismissing
    the modal doesn't leave editing silently dead.
    APP_DATA_VERSION (src/version.js) is the ordinal. A build SHA says two
    builds differ, never which is newer — that is why the gate needs its own
    number and can't reuse catalogVersion, which moves when a USER presses
    Export.
    The fix that made any of it work: main.jsx registered the service worker
    once and never called registration.update() again, so an app left in memory
    never learned a new build existed. It now checks on visibilitychange and on
    reconnect.
    The gate seeds from the CACHED catalog as well as the live listener —
    offline the listener never fires, and "the last catalog I saw was newer
    than me" is exactly when writing does damage. isBuildTooOld answers no to
    anything unparseable and fires only on strictly greater.
    STILL UNVERIFIED: the gate firing against a genuinely old build. Test with
    production in one browser and a PR preview in another, same household.

33. [DONE] Fixed the two require-atomic-updates races in sync.js, by
    sequencing rather than by racing to commit the newest baseline — the
    second option the item sketched, chosen because it removes the ambiguity
    by construction instead of needing a way to compare "newest".
    doWriteCatalog and doFlush (the actual network calls) now run through a
    tiny per-node queue (sequencer(): a chained `tail = tail.then(fn)`), so a
    second write's read of lastCatalog/lastWritten can never happen until the
    first write's has fully landed — no overlap, no ambiguity about which
    await resolves last.
    THE LINT RULE STILL FIRES, because require-atomic-updates is syntactic:
    it can't see that the sequencer makes the read-then-write-after-await
    pattern safe. Two targeted eslint-disable-next-line comments cover the
    exact lines, each explaining why — the first eslint-disable comments
    anywhere in this codebase, and a legitimate use of one: the rule's
    underlying concern is actually addressed, just not provably so from where
    it's looking.
    Verified by rapid-fire browser test — three recipes added back-to-back
    (writeCatalog) and three hand-added list items back-to-back
    (writeHousehold) — all landed with nothing lost, exercising exactly the
    overlap this item was about.
    Done together with item 20 — same file, same theme.

34. [DONE] Put the Firebase security rules in the repo, and published them.
    There was no rules file under version control — README.md carried an
    inline copy instead, which is not diffable and could quietly drift from
    whatever was actually live on the console.

    database.rules.json is now that source of truth, with firebase.json and
    .firebaserc alongside it so `firebase deploy --only database` targets the
    right project without extra flags. README.md's setup steps point at the
    file instead of embedding their own copy.

    WHAT IT DOES: deny listing every household at `/households` (nothing
    grants that read; only `$code` does, so only a specific known code
    resolves to anything); require `$code` to match cleanCode()'s own alphabet
    and be 8-40 characters (the README's prior inline rule only checked
    length, no character class); and validate that `updatedAt` — present on
    every write to state and catalog — is actually a number, catching a
    malformed payload rather than corrupting the shared blob.

    DELIBERATELY SHALLOW. No schema validation beyond those three scalars.
    normalizeLocal spreads `...d` specifically so an unrecognised field
    survives a build that doesn't know about it yet (tested in lib.test.js) —
    a strict `.validate` schema at the database layer would silently defeat
    that same guarantee from underneath the app, rejecting a legitimate
    future field the app itself is built to tolerate.

    PUBLISHED via the console's Rules tab (pasted from database.rules.json),
    not the CLI. Nothing in the build or CI touches the deployed rules — the
    committed file and the live database are two separate things kept in sync
    by hand, same as before this item except now there is a diffable copy to
    paste FROM. If the rules ever need to change again, that's still a manual
    republish, not something a merge triggers automatically.
    STILL NOT INDEPENDENTLY VERIFIED FROM THIS SIDE: nothing in this session
    can reach the Firebase console, so whether the deployed rules exactly
    match database.rules.json rests on the paste having gone cleanly. Worth
    a quick real check next time both phones are open — sync still working
    confirms it; item 20's write-error signal would surface it immediately if
    something in the paste was off.

    Real fix is auth — see FutureProjects.md and item 37.

35. [DONE] Add an error boundary. A render throw used to give a white screen,
    in a shop, with no way back. A class component in main.jsx now wraps
    <App/> and renders a "Something went wrong" fallback with a Reload
    button on any render throw. Reload is enough to recover because state is
    already on disk (loadCache) before anything renders — the boundary
    doesn't need to hold or restore it itself.
    Verified by mutation test: App() temporarily made to throw behind a
    query param, confirmed in a real browser (playwright-core against
    `vite preview`) that the fallback renders and Reload works, then
    confirmed the normal build shows no trace of the fallback. Change
    reverted before committing.

36. Split lib.js WHEN IT MAKES A CHANGE HARD, not on principle. It is 1,222

39. INGREDIENT LINES NEED A THIRD FIELD, and this is the root of several

    SIGNING IN DOES NOT ADD AN ACCOUNT TO EVERY HOUSEHOLD. Checked
    deliberately, because two separate households ended up holding both
    accounts and that looks exactly like a fan-out bug. It isn't one, and
    four independent things prevent it:
      - there is ONE write to any members path in the whole codebase.
      - it has ONE caller, which passes the single currently-selected
        `code` — a scalar, never a collection.
      - no code anywhere references `households` without a `${code}`
        segment, so nothing can enumerate them, which a fan-out needs.
      - /households itself has no `.read`, so the database refuses to list
        households even if a client tried.
    Empirically: six of the eight households have no members node at all.
    A fan-out would have written to all eight. What actually happened is
    that one browser session moved between two household codes and two
    accounts inside 76 seconds, and each write recorded the (code, account)
    pair that was active at that moment — which is the intended behaviour.
    The extra households are test litter, mostly from browser-driven
    verification: firebase-config.js commits a real databaseURL and
    syncEnabled is just Boolean(databaseURL), so ANY browser loading ANY
    build talks to the production database and mints a code on first run.
    Worth deleting them from the console before CONTRACT, since after it
    the two that hold both accounts would otherwise read as real
    households.

    [BUILT, NOT YET DEPLOYED] CONTRACT. database.rules.json now requires
    BOTH a real identity and a membership record to read or write a
    household. There is deliberately no unauthenticated fallback: a device
    that isn't signed in reads and writes nothing. Done as one step rather
    than a transition window with an `auth == null` branch, because the
    second phone is being signed in as part of delivering this — a window
    nobody needs is two pastes and two rounds of app changes for nothing.
    members/$uid needed its own ".write" (it had only ".validate"). The
    $code-level ".write" now requires membership, so the account that needs
    that write is precisely the one that isn't a member yet; without a
    deeper grant, joining is impossible by construction — the write that
    makes you a member would require already being one. That deeper grant is
    the one door into a household, and it opens only at the caller's own uid.
    Access is now identified and enumerable. Self-service joining is GONE
    as of the invite work below, so removal actually sticks.

    REQUIRING AUTH FORCED APP WORK, and it is the more interesting half.
    Once a signed-out phone is refused everything, the app had three ways to
    lie about it:
      - THE GREEN DOT. syncStatus comes from watchConnection, which reads
        .info/connected — a client-side path NO security rule gates. It
        reports "synced" perfectly happily while every read is refused, so
        a signed-out phone would have shown "Synced" over a dead listener.
        That is precisely the "looks fine, syncs nothing" failure this
        codebase keeps paying for. The precedence now lives in
        syncIndicator() in lib.js: sign-in state and authorization both
        outrank connection state, and connection is LAST because it's the
        one the database can contradict. Each case is the CAUSE of the ones
        under it — "Sign in to sync" says what to do, where "No access",
        equally true at that moment, leaves you guessing.
      - A SILENT DENIAL. onValue had no cancel callback, so permission_denied
        did nothing at all — indistinguishable from "connected, nothing has
        changed yet". subscribeHousehold/subscribeCatalog/subscribeMembers
        now take onError. Two properties matter: Firebase REMOVES a listener
        it cancels, so a denial is terminal and only a resubscribe recovers;
        and cb is never called on a denial, so a refused read can't arrive
        as `null` — which would read as "no household here, seed it" and
        turn a permissions problem into a write.
      - THE COPY. Settings still said sign-in was "optional, and doesn't
        change anything yet". It is now the thing that grants access.
    IT IS IN lib.js, NOT App.jsx, FOR A SPECIFIC REASON: the case that
    matters most — a socket genuinely CONNECTED while reads are refused —
    cannot be reproduced in a browser here, because this sandbox can't reach
    Firebase at all and the socket just reads offline. A pure function takes
    no network. Six tests cover it, and both mutations were confirmed:
    moving the "synced" check above the authorization checks fails exactly
    the three tests about precedence, and dropping the authReady guard fails
    exactly the one about not claiming "signed out" before auth has
    answered.
    authReady exists because `user === null` means two opposite things —
    "don't know yet" before Firebase answers, "nobody" after. Auth restores
    asynchronously, so treating the initial null as signed-out would flash
    "Sign in to sync" on every launch of a signed-in phone.

    THE RESUBSCRIBE RACE, found while reasoning about the rules and fixed
    with them: the household/catalog subscribe effect only re-ran on `code`,
    never on `user`. A device signing in AFTER that effect's first run — the
    common case, since auth restores after mount — would have its listener
    denied and never retried. It now depends on a `membershipTick` bumped
    once recordHouseholdMembership's write actually LANDS, not the instant
    sign-in state changes, which would still race the write and just get
    denied again.
    Work done while signed out is not lost: updateCatalog and setLocal still
    write to localStorage, and pickState pushes whichever copy is newer once
    the listener is allowed again. So signing in flushes what the phone did
    while it couldn't reach the database.

    [BUILT, NOT YET DEPLOYED] INVITES — the step that makes removing
    somebody mean something. Before it, membership was self-service: any
    signed-in account holding the code wrote its own record, so taking a
    member out was decoration — they knew the code, so they rejoined.
    An account now becomes a member exactly three ways, all concentrated in
    the members/$uid ".write":
      1. it already has a record (refreshing it, or deleting it to leave)
      2. the household has NO members — first claim, which a brand new code
         needs and which no occupied household can be turned into
      3. it presents an unexpired invite token created by an existing member
    Plus one exception that only ever TAKES access away: a member may DELETE
    another member's record, never create or edit one.
    An invite is households/{code}/invites/{token} = { by, byEmail,

    THE REDEEMER DELETES IT AS A SECOND WRITE, not atomically with joining.
    At the moment of redeeming they aren't a member yet, and letting a
    non-member delete invites would let anyone holding the code burn every
    outstanding one — a denial of service on joining. Doing it immediately
    after works because by then they ARE a member; if that write is lost the
    invite just expires.

    code. One field in Settings takes either, since a user handed a string
    shouldn't have to classify it.

    [BUILT, NOT YET DEPLOYED] THE GUEST ROLE. Someone you hand a link to so
    they can do the shop: reads everything, writes only the List tab.
    Reading the whole household is deliberate — a list of names with no
    recipes behind it isn't shoppable, you can't tell what a thing is for.
    members/{uid}.role is "guest", or absent/"member" for full. ABSENT MEANS
    FULL, which is what makes this backward compatible: the records written
    during EXPAND have no role and belong to the two people who own the
    household.
    HOW IT'S ENFORCED, and the shape is worth remembering: households/$code
    ".write" became full-members-only, and the guest's permissions are
    re-granted BENEATH it at state/list, state/stapleNeeds and
    state/updatedAt. A deeper ".write" adds permission where a shallower one
    denied, so denying at $code and re-granting narrowly is what produces
    "everything except these paths is read-only". updatedAt has to be in the
    list because every narrow write carries it; without it a guest's write
    would be half-refused and the other phone would never see the change.
    NOT re-granted, deliberately: plan and planStage. Planning the week and
    starting or ending a trip belong to the household.

    THE ESCALATION THAT ALMOST SHIPPED, caught by a test. Every member
    rewrites its own record on each load, so a guest could simply write
    role: "member" and promote itself. The fix is role immutability — but
    the FIRST attempt put that check in members/$uid ".write", where it
    silently did nothing for the people it mattered least about and
    everything for the people it mattered most about... backwards: the
    $code-level ".write" grants a FULL member everything beneath it, and a
    deeper ".write" can only ADD permission, never take it back. So the
    check constrained guests and strangers but did not apply to full members
    at all. It lives in ".validate" now, the only rule kind that always
    runs. A second test caught the corollary: ".validate" doesn't run on
    deletes, which is what lets a guest still leave.
    A knock-on: the membership refresh had to move from set() to update(),
    because a set() that drops `role` reads as CHANGING it and is refused.

    THE ROLE RIDES IN THE INVITE STRING ("code~token~g"), because the
    account redeeming an invite cannot read it — invites are members-only
    and a joiner isn't one yet. That is not where it's enforced: the rules
    require the record written to match the STORED invite, so editing the
    "~g" off a link is refused rather than upgraded. Tested both ways round,
    including the quieter direction — omitting the role entirely, which
    would otherwise default to full.
    parseInvite got stricter with it: a third segment that isn't exactly "g"
    is now refused outright rather than folded into the token, so a mangled
    guest link can't resolve to a full membership.

    THE APP MIRRORS THE RULES RATHER THAN LISTING TABS. guestBlockedFields
    (lib.js) says "everything except list, stapleNeeds and updatedAt is off
    limits", checked against the RESULT of an edit in App's update(). That
    catches every route into a forbidden field, including ones that don't
    exist yet — a new top-level field is denied to a guest by default,
    exactly as the rules do. Gating per tab would have meant auditing four
    tabs and re-auditing on every feature. updateCatalog is stopped once,
    centrally, since the whole catalog is full-members-only.
    A refused edit gets a sentence naming what's off limits, not the generic
    "Sync error" a rejected write produces.
    [DONE] THE BUTTONS A GUEST CAN'T USE ARE NOW HIDDEN, not disabled — a
    greyed-out "Clear week" asks how to un-grey it, and the answer isn't
    something a guest can do. What goes: creating and editing recipes,
    everything on the week plan, the stores card, adding an ingredient, and
    a row's store/aisle/staple/rename/remove. What STAYS, because it is a
    list write or a read: adding a meal to the list, the whole List tab, the
    "used in / on the list" footer, and every tab remains visible — a guest
    needs the recipes and the week to know what the list is for.
    Settings' Preferences and Restore go too; saving a backup is a read and
    stays.
    TESTABLE AT ALL ONLY VIA A SEAM: guest-ness comes from a members/{uid}
    record, which a sync-stripped build can never hold, so the guest UI would
    have been unreachable in the e2e suite. GUEST_PREVIEW_KEY is read ONLY
    when syncEnabled is false — a production build takes the real branch and
    never looks at it, and the rules refuse the writes regardless of what any
    client believes.
    EVERY CASE ASSERTS BOTH DIRECTIONS, because hiding too much is the easier
    mistake and the harder one to spot: the thing a guest must not see is
    absent AND a full member still sees it. Mutation-tested both ways —
    showing the editors to a guest fails the guest case, hiding them from
    everyone fails "a full member still sees everything".
    A TEST BUG WORTH REMEMBERING: Playwright's `has-text` is a
    case-insensitive SUBSTRING match, so `button:has-text("Edit")` matched a
    recipe called "M-edit-erranean Baked Crispy Chicken" and reported a guest
    being offered two Edit buttons that did not exist. Use `text-is` for an
    exact button label. The member control is what made this legible as a
    selector fault rather than an app fault.

    Rules coverage went 24 -> 38 cases, all against the real emulator.
    Mutation-tested: removing role immutability fails exactly the two
    promotion/demotion cases; giving guests the full $code write fails seven.

    [BUILT, NOT YET DEPLOYED] FIRST RUN, AND GUEST LINKS THAT DON'T NEED AN
    ACCOUNT. Two problems, one cause: nothing on screen ever told a new
    browser what to do. It minted its own household code and landed on a
    working list seeded from catalog.json — which LOOKS fine, and that is
    the trap. Someone handed an invite ended up in a private household of
    their own, staring at a list that wasn't the shared one, with nothing
    suggesting anything was wrong. The app was answering a question they
    hadn't asked.
      - src/Onboarding.jsx: three ways in, the one most people arrive with
        (a link somebody sent) first, then signing in, then "start my own
        list". Shown ONLY to a browser with no household data and nobody
        signed in, so neither of the two existing installs ever meets it.
        Gated on authReady for the same reason the sync indicator is: `user`
        is null before Firebase answers, so without it a signed-in phone
        would flash the first-run screen at every launch.
      - ANONYMOUS AUTH for guest links. A guest link now signs the browser in
        anonymously and asks for a name, so being handed a link is the whole
        flow — no account to make. Chosen over requiring a real sign-in
        because a guest is inherently a one-off: the friction of an account
        is most of the cost of asking someone to do the shop.
        THE COST, stated plainly: the identity lives in that browser's
        storage and dies with it, so clearing site data means asking for a
        new link. The typed name is what keeps the member list answerable —
        without it a guest shows as a bare anonymous id, which would undo
        most of what CONTRACT was for.
        NEEDS THE ANONYMOUS PROVIDER ENABLED in the console, same manual
        step as Google and email-link.
      - THE RULES CAP IT HARD, and this is the part worth keeping:
        auth.token.firebase.sign_in_provider != 'anonymous' now guards case 2
        (first claim) and full-invite redemption. An anonymous identity may
        be a guest and nothing else — it can't own a household and can't hold
        one as an equal, because both should mean an account that can be
        recovered and named. Mutation-tested: dropping the guard fails
        exactly the two cases that assert it.
      - A KNOCK-ON WORTH REMEMBERING: recordHouseholdMembership refreshes the
        member record on every load, and it used to send email/displayName as
        `|| null`. For an anonymous guest both are null on the auth user —
        the name exists ONLY in the member record — so the refresh would have
        wiped the typed name on the next load. It now sends only the fields
        it actually has.

    SETTINGS SAYS "HOUSEHOLD" NOW, not "Phone-to-phone sync". That name was
    the old model — a shared code WAS the whole story, and hasn't been since
    membership landed. Members and invites were buried underneath it, which
    is exactly backwards: they are what the section is for now, so they come
    first and the code drops to the bottom as the detail it has become.
    Opens by default, because it is the thing you go to Settings for.

    THE E2E HARNESS NEEDED A CONCEPT IT DIDN'T HAVE. openApp seeds a device
    code but no state, so with the first-run screen live every existing spec
    suddenly landed on it and timed out looking for a tab bar. It now seeds
    the onboarded flag by default (these specs test the APP), with
    onboarded:false to opt out. The WAIT TARGET mirrors the app's own rule —
    cached state counts as onboarded there, so seeding `state` means the app
    screen even with the flag withheld. Deriving it any other way makes the
    harness disagree with the thing it is testing, which is how a harness
    starts lying.

    WHAT'S LEFT
      - ENABLE THE ANONYMOUS PROVIDER in the Firebase console (Authentication
        -> Sign-in method), or guest links fail at the sign-in step with a
        message rather than working.
      - DELETE the throwaway home-* households in the console FIRST. After
        CONTRACT the two holding both accounts would read as real ones.
      - SIGN BOTH PHONES IN **BEFORE** PASTING, and check each shows up in
        Settings' member list. Both accounts already have member records
        from the EXPAND phase, so nobody is locked out by the paste — but a
        phone that is signed OUT when the rules land stops syncing on the
        spot. Nothing is lost when that happens (edits keep saving locally
        and push once it's allowed again), it just looks broken.
      - PASTE database.rules.json (same manual step as item 34).
      - VERIFY ON BOTH PHONES afterward. Three things, none of which this
        sandbox could check because it has no path to Firebase:
          * sign out and back in mid-session — the list must resume
            updating rather than going quietly stale (the resubscribe path).
          * invite the other account end to end, from a real Settings
            screen. Two browsers and two emails is enough — an invite is
            accepted for an ACCOUNT, not a device, so two profiles signed
            in as different accounts exercises the real path.
          * hand a GUEST link to the second account and confirm the shape
            of it: the list works, and recipes / ingredients / the week
            plan refuse with the guest banner rather than failing silently.
          * remove an account and confirm the code alone does NOT let it
            back in. That is the whole point, and the only proof that
            matters is the live database.
      - Narrow listeners: item 21's read half. Still deliberately deferred,
        and the catalog move made the case WEAKER rather than stronger, since
        the growth landed on its own node instead of on `state`.
      - Hide the controls a guest can't use (Meals, Week, Ingredients).
        They explain themselves when tapped today, which is honest but not
        as good as not offering them.
      - Billing, a landing page. Ordinary product work, no foundation
        questions left in them.
        On roles: guest/member is now the whole ladder, and every FULL
        member is equal — anyone can remove anyone, including the account
        that created the household. Fine for two people who live together;
        an owner who can't be removed is the next rung if a third full
        member is ever in one.

    Firestore is not a step here. It becomes worth adopting when one of its
    advantages actually binds — most likely offline persistence, or history
    outgrowing what a client-side slice can page through. Item 21 covers what
    keeps that door open.

38. A nicer URL than stuart-belcke.github.io/grocery-run/. Came up while
    walking through Authorized domains for item 37 — the current URL works
    fine but looks like a personal project tucked under an account, not
    something you'd hand to someone else.
    DECIDED: not worth a purchased custom domain right now. A domain is
    ~$10-15/year for something purely cosmetic today; only actually buy one
    if some future distribution requirement forces it — e.g. listing this
    somewhere (an app store, a share link that has to look legitimate) that
    itself demands a real registered domain. Revisit if that happens, not
    before.
    THE FREE OPTION, if/when the current URL is worth improving without
    paying: a GitHub Organization (not a second personal account — no extra
    login to manage) named grocery-run gets grocery-run.github.io for free,
    the same way any account's own `<name>.github.io`-named repo does.
    What that would actually take, so it isn't underestimated as a five-
    minute change:
      - create the free org, transfer this repo into it, rename the repo to
        grocery-run.github.io (the exact name is what unlocks the root URL
        instead of a subpath).
      - .github/workflows/deploy.yml builds URLs assuming a PROJECT site
        (`<owner>.github.io/<repo>/`) today — both the live-site verification
        curl and the PR-preview mechanism need checking against a root-served

      - add grocery-run.github.io to Firebase Auth's Authorized domains
        (additive — stuart-belcke.github.io doesn't need removing, in case

      - the app itself needs NO changes — vite.config.js's `base: "./"` was
        already deliberately built to work at any URL depth, checked when
        this question came up.
    Not scheduled. Written down so the org-vs-domain tradeoff doesn't need

Refactor notes
--------------
[DONE] The catalog move was done as EXPAND then CONTRACT, and it's the pattern
  to reuse for any future shape change that two devices have to survive.
    expand   — the new path (households/{code}/catalog) is added and read, and
               the old fields are left in place, written by nobody and read by
               nobody. Rolling back is reading them again, not restoring a
               backup. Shipped as one release, then actually used on two phones
               for a day.
    contract — the old fields come out of the code once the new path is proved.
  Two things made the contract step cheap. normalizeLocal spreads `...d`, so
  retiring a field carries it through instead of pruning it — there is no
  migration write to get wrong, and a device that never saw the new build keeps
  its copy. And every reference was in lib.js by then, because the read half had
  already moved in the expand release.
  The traps, both caught by tests rather than by reading: validLocal gated on
  localRecipes existing, so removing it from emptyLocal would have made every
  new device's state read as invalid; and needsKeyMigration checked localRecipes
  for a legacy array shape, which after the contract would force a needless full
  set() to repair a disagreement that no longer exists.

[DONE] App.jsx was split so each feature edits a small, reviewable surface:
  - theme.js + ui.jsx: UI primitives (colors, fonts, Btn, Seg, Stripe, inputStyle)
  - lib.js: pure helpers (constants, catalog/config normalization, storage,
    model normalization, list aggregation)
  - src/tabs/*.jsx: per-tab components (List, Meals, Week, Pantry, Settings)
App.jsx itself is now ~265 lines, just wiring the tabs together.

[DONE] `usedInRecipes(data, key)` centralized in lib.js. PantryTab.jsx's three
inline copies of `data.recipes.filter/some((r) => r.ingredients.some((i) =>
norm(i.name) === key))` — the rename-affected-recipes check, the remove-item
safety check, and the item 9 "used in" display — all call it now.

[DONE] Back to top on List, Ingredients and Meals. Both lists outgrow what anyone
will scroll back through by hand — the real catalog makes the Ingredients tab
about 8,500px — and search doesn't help: you search to FIND something, and are
then left wherever the list left you.
  A corner button, not a fourth control in the StickyBar. That row was cut down
  to search + one Filter button + the primary action precisely so it holds one
  line at 390px, and the bottom-right corner is under a thumb where the top of
  a phone screen is not.
  A scroll listener rather than StickyBar's IntersectionObserver, and the
  difference is the question each asks: the bar wants "has this element reached
  the top", which is what an observer reports, and this wants "how far down are
  we" — a distance an observer can only fake with sentinels at guessed depths.
  Passive, coalesced to one requestAnimationFrame.
  THREE THINGS ONLY A BROWSER SETTLES, all covered by
  tests/e2e/specs/backtotop.spec.mjs and all mutation-tested (never showing it,
  always showing it, and z-index above the dialog each fail exactly the right
  cases): it renders only past a scroll depth; it is position:fixed inside a
  page that already has a position:sticky bar creating a stacking context, so
  it can be painted but not tappable; and at z-index 20 it must lose to the
  dialogs at 70. The spec hit-tests the corner with elementFromPoint rather
  than trusting visibility, because "visible but something else owns that
  pixel" is exactly the failure that looks like a dead click handler.
  Unusually for that suite there is nothing persisted to assert on — this is
  pure UI, so the read-back rule doesn't apply.
  IT SHIPPED READING THE SIX LITERAL CHARACTERS \u2191, and the first version
  of this spec did not notice. JSX does NOT interpret a \uXXXX escape in a
  text child — only inside braces, which is why Section's chevrons were fine
  — so the button rendered gibberish while working perfectly. The test
  asserted the aria-label, the appear/disappear threshold, the hit test and
  the scroll, every one of which passed. THE LESSON IS NARROW AND WORTH
  KEEPING: behaviour assertions do not see the label, so anything a user
  READS needs asserting as text. The spec now checks the rendered glyph, and
  reintroducing the bug fails all three tabs.
  The List tab needed a fixture to be worth testing at all: it is empty in
  every other one, so the scroll test would have passed by never scrolling.
  longListState() in fixtures.mjs fills it with hand-added extras, which need
  no catalog, plan or recipes.
