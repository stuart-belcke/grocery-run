Grocery Run — Roadmap
=====================

A single, prioritized backlog combining the earlier scattered notes with the
newer batch of ideas. Duplicates and closely-related items have been merged.
Tiers are ordered: cheap high-impact UX wins first, then the Ingredients-tab
cluster (which shares a refactor), then data-model changes, then the riskier
multi-device / integration work last. A Hygiene section after Tier 4 collects
the work that isn't a feature — tests, shared logic, and the database seam.


Tier 1 — small, high-value, low-risk
------------------------------------
1. [DONE — #11, #12] Recipe detail view. Tapping a recipe card in the Meals
   tab expands its full ingredients + notes, read-only, without having to hit
   Edit.
2. [DONE — #11] Remove a meal from "the list". After "Add to list" from the
   Meals tab, give an explicit way to take it back off. Also handle meals that
   reached the list via the Week plan, not just the Meals tab.
3. [DONE — #11] Suggested "unit" values when adding a new item.
4. [DONE — #11] Move the settings section off the bottom of the Ingredients
   page into a dedicated Settings tab (or a hamburger menu at the top). Do
   this before adding search/filter to the Ingredients tab so it isn't
   cluttered.
5. [DONE] Checked-off items: gray only the name, not the details. The whole
   List row no longer dims on check — only the item name gets the
   strikethrough + dim, so expanding a checked item keeps its "On the list
   for" breakdown at full opacity and legible.
6. [DONE] Week-plan meal picker. Each day/meal slot is now a tap-to-open
   button (showing the assigned meal, or "＋ Choose a meal") that opens a
   searchable modal mirroring the Meals tab — a search box plus recipes
   grouped "{type} meals" / "Other meals", each showing servings + tags, with
   the current pick checked and a "Remove meal from this slot" option. Replaces
   the native <select> that didn't fit the app's feel or scale with the list.


Tier 2 — Ingredients-tab cluster (shared refactor, then features)
-----------------------------------------------------------------

   narrows to items with that default store. List stays A-Z sorted.
9. [DONE — #17] Ingredient rows show which recipes they're used in (inside
   the expanded gear panel, alongside whether it's also hand-added to the
   list) rather than as a separate info icon.
10. [DONE — #17] Add ingredients to the shopping list straight from the
    Ingredients tab. Each row gets a "+ List" button that becomes a
    ± quantity pill (with a tap-to-type-exact-amount) once it's on the list,
    defaulting to whatever unit recipes most commonly measure it in.
11. [DONE — #17] The List tab's "add an item" field now suggests matching
    known ingredients as you type (name + default store, keyboard-navigable),
    so you pick an existing item instead of creating a duplicate.
12. Suggest units as you type when adding a new ingredient. Extend the unit
    suggestions (item 3) to the ingredient-adding flow — the recipe editor's
    add-ingredient row and the Ingredients tab — offering the units already in
    use as you type. Must still let you type a brand-new unit and use it; the
    suggestions never restrict entry to a fixed set.

    UNIT CONVERSION — do this as part of the same "take units seriously" pass.
    Nothing converts today. aggregateItems keys an item's `parts` by the raw
    unit string, so equivalent amounts never combine:
      - a recipe wanting 1 lb and another wanting 8 oz list as "1 lb, 8 oz"
        instead of 1.5 lb
      - `list.bought` subtracts per unit, so buying 1 lb does NOT offset a
        recipe asking for 16 oz — it stays on the list looking unbought
      - unitForKey (the staple quick-add default) just picks the most common
        unit, with no notion that others are the same thing
    So it bites in three places, and the shopping-list one is the costly one:
    it can make you buy something you already have.

    What a conversion layer needs:
      - units grouped by DIMENSION (weight / volume / count) with a factor to
        a base unit per dimension — lb→oz ×16, kg→g ×1000, l→ml ×1000,
        cup→tbsp ×16, tbsp→tsp ×3
      - conversion only WITHIN a dimension. oz (weight) and fl oz (volume) are
        different things, and "can" / "bunch" / "head" convert to nothing
      - unknown and free-text units must keep working untouched, just
        unconvertible — the app deliberately lets you invent a unit, and that
        can't regress (see the rule above)
      - display picks the most readable unit for the total (1500 g → 1.5 kg)
        rather than always normalizing to the base
    Deliberately out of scope: weight <-> volume. That needs per-ingredient
    density (a cup of flour and a cup of water differ), which is a much bigger
    data problem than a factor table.

    Where it lives: a table in lib.js beside COMMON_UNITS, which is already the
    unit vocabulary. Additive — existing data keeps working because anything
    not in the table simply doesn't convert. If it should be editable per
    household rather than hardcoded, it could ride in catalog.json like stores
    and ingredient config, but start hardcoded; these factors don't vary.


Tier 3 — data-model / sorting
-----------------------------
13. [DONE] Pantry staples. Built as specified below; the spec is kept as the
    record of what was decided and why.

    THE PROBLEM
    Recipes call for olive oil, garlic, flour, salt. Every week those land on
    the shopping list even though you already have them, so the list is padded
    with things you don't need to buy.

    THE MODEL: persistent have/need, not a weekly quiz
    A staple carries a persistent state that only changes when reality changes:
      - "have"  (default) — invisible, stays off the shopping list
      - "need"  — appears on the shopping list
    You flip it to "need" the moment you notice you're out (Tuesday night, when
    you pour the last of the oil), not by trying to recall it on Sunday. Most
    weeks you touch nothing and the review is empty.

    Two consequences worth noting:
      - It decouples staples from meal planning. "We need olive oil" is true
        because you ran out, not because a recipe wants a tablespoon. Paper
        towels and coffee behave identically to recipe ingredients — one
        mechanism, no special case for non-recipe items.
      - Anything you didn't manage to buy stays "need" and carries forward to
        the next list automatically. No re-entry.

    NO PARALLEL DATA STRUCTURE
    A staple is an ordinary catalog ingredient with a `staple: true` flag on its
    existing config entry. Same { store, aisles }, same identity, same
    everything. "The staples list" is only ever a VIEW — a filter over the
    ingredients that already exist. Nothing to migrate, nothing to keep in sync.

    DATA MODEL — two halves, two sync routes (this split is the important part)
      config[key].staple = true
        Durable designation. Lives in ingredient config, rides configOverrides
        to RTDB, AND publishes to catalog.json. A shared fact about the kitchen.
      stapleNeeds = { key: true }
        Volatile "we're out" state. New TOP-LEVEL key in local, sibling to
        `list` and `plan`. Syncs to RTDB (writeHousehold writes the whole local
        object, so this is free) but is NEVER published — otherwise every "out
        of garlic" would be a git diff in catalog.json.
      Store only the "need" keys; absence means "have". Firebase strips empty
      objects, so once all are back to "have" the key vanishes from RTDB and
      asObject() rebuilds it as {} on the way in. Self-healing.
      Requires: `stapleNeeds: {}` in emptyLocal(), and
      `stapleNeeds: asObject(d.stapleNeeds)` in normalizeLocal().

    TWO GOTCHAS IN EXISTING CODE (quiet bugs if missed)
      - normalizeCfg() (lib.js) returns only { store, aisles }, so it would
        SILENTLY STRIP the staple flag. The publish path (SettingsTab) runs
        every config through it, so staples would vanish on publish.
      - cfgShape() (lib.js) hashes only { store, aisles }, so toggling a staple
        wouldn't register as an unpublished change and the "N not yet
        published" badge would be wrong.

    WHY NOT PER-TRIP STATE
    An earlier design put the have/need answer in `list` and wiped it each
    trip, prompting a full review every week. Rejected: it forces recall
    instead of capture, and the review burden grows with the recipe
    collection. Persistence is the whole point — hence the top-level key,
    deliberately outside `list` and `plan`, which newList() clears.

    UI
      - Designating a staple: a checkbox in the Ingredients row's expanded gear
        panel ("Home staple", 🏠). Set-once and rare, so it stays off the
        collapsed row.
      - Toggling have/need: on a staple row the "+ List" button is REPLACED by
        a Have/Need toggle — on a staple the two would mean the same thing to
        the user, so only one control shows. Non-staple rows keep "+ List".
      - Managing / reviewing: a "Staples only" filter on the Ingredients tab,
        reusing the existing search + store-filter machinery. Near-zero new UI.
      - On the shopping list: a "need" staple sorts into its NORMAL store/aisle
        group (it keeps its real store), shown inline with a small "staple"
        tag — not a separate section, so you walk past it in the right aisle.
        No quantity: it means "get more", not "get 2 lb".

    CLEARING THE LOOP
    Rename "New shopping list" -> "Done shopping" (it marks the end of a trip).
    On that action, any staple that was CHECKED resets to "have"; unchecked
    ones stay "need" and carry to the next list — you didn't get it, maybe the
    store didn't have it, so it stays pending. Don't clear on the checkbox
    itself: the item would vanish from the list mid-aisle.

    "Done shopping" was later narrowed, because one button was resetting six
    things at once. The rule now: what you CHECKED OFF is done with, what you
    didn't get carries forward.
      - EVERYTHING checked comes off the list — you own it now. Hand-added
        items are deleted outright. Recipe-driven items can't be (they're
        computed from the plan we're keeping), so the AMOUNT bought is banked
        in `list.bought` as { key: { unit: qty } }. The List tab is a shopping
        list, not a recipe viewer — what a recipe contains belongs on the
        recipe card.
        `bought` records quantities, not a boolean, and aggregateItems
        SUBTRACTS it from current demand rather than hiding the item: buy 1 lb
        of beef for one meal, then plan a second wanting 2 lb, and 1 lb is
        still listed. Only fully-covered items drop off. A boolean here was a
        real bug — the second meal would have been silently under-bought.
        Hand-added amounts are tracked separately (item.handParts) and are
        never cancelled by the cupboard, since typing something onto the list
        is an explicit "buy this". Staples are skipped entirely: they run on
        have/need, not amounts.
      - unchecked items of every kind stay listed
      - checked staples go back to "have"; unchecked stay "need"
      - check marks and meal selections clear
      - store reroutes survive only for items still on the list
      - the WEEK PLAN is untouched. "Clear week" on the Week plan tab owns it;
        wiping a week's planning from the shopping list was a far bigger reset
        than finishing a trip implies.
    "Clear week" also empties `list.bought`, ending the buying cycle, so the
    next week's meals list their ingredients again from scratch. A count of
    suppressed items shows on the List tab ("N already bought this week") so
    the list is never mysteriously short.

    DECIDED AGAINST (for v1)
      - A third "low" state. Binary can't express "have half a cup, recipe
        wants three" — accepted. The whole value is low friction and a third
        state doubles the decisions; the pre-shop glance catches it.
      - A "anything else run out?" scan over have-it staples. Re-introduces the
        weekly chore the persistent model exists to remove.
14. [DONE] Once an item is checked on the List, move it to the bottom of its
    group and keep following the A-Z / store-flow sort the user has selected.
15. [DONE] Recipes reference the shared ingredients list to avoid duplicates.
    The recipe editor's ingredient-name field now suggests matching known
    ingredients as you type (name + default-store hint, keyboard-navigable),
    reusing item 11's List-tab pattern, so you pick an existing item's exact
    spelling instead of forking a spelling variant into a separate ingredient
    and shopping-list line. Recipe ingredients still store { name, qty, unit };
    the suggestions steer them onto canonical norm(name) identities.

Hygiene — not features, and not sequenced
------------------------------------------
None of these ship anything on their own. They're what keeps the app cheap to
change: a test layer, one place for shared logic, and a database seam narrow
enough to swap what sits behind it. Do them alongside whatever feature is next
rather than saving them for a cleanup that never gets scheduled.

19. Tests on the pure layer. There is no test framework at all — every fix so
    far was verified by driving a headless browser by hand, which doesn't
    scale and doesn't survive working in a hurry. lib.js is the cheap win:
    pure functions, no DOM, no Firebase, and it is where the subtle bugs have
    actually lived. Start with aggregateItems (bought subtraction, hand-added
    parts, staple suppression), pickState, normalizeCfg / compactCfg, and
    unpublishedChanges. Every one of those has already shipped a real bug.

20. Make a failed write visible. writeHousehold logs a rejection to the
    console (sync.js:162) and nothing else. The header dot reports CONNECTION
    state, not whether data landed, so a rules rejection looks identical to a
    healthy app while edits quietly disappear. Surface it in the UI the way
    the offline state already is.

21. Keep the database seam narrow. Every database call lives in sync.js, and
    App.jsx is the only component that touches sync at all (SettingsTab
    imports syncEnabled and cleanCode — a boolean and a string helper). That
    property, not any clever abstraction, is why RTDB could be swapped for
    Firestore in days rather than weeks. Defend it deliberately as usage
    grows and the right database stops being obvious:
      - no `firebase/*` import outside sync.js. Add an ESLint
        no-restricted-imports rule so it can't regress silently.
      - the seam should say WHAT CHANGED, not hand over everything.
        toggleChecked(key, on), not writeHousehold(entireState). RTDB
        implements that as a write at one path; Firestore as a document
        update. Neither is forced into the other's shape.
      - this also retires the update() footgun. Two update() calls in one
        handler discard the first, because both rebuild from the same stale
        snapshot — that is what broke the staple checkbox, and a comment on
        the function is not enforcement. Narrow writes remove the constraint
        instead of documenting it.
      - do NOT abstract queries or offline storage. Those genuinely differ
        between the two databases and a wrapper inherits the weaknesses of
        both. Keep filtering in JavaScript, and keep loadCache/saveCache as
        thin as they are — a Firestore migration deletes them outright rather
        than porting them.

    THE READ HALF IS STILL OPEN, AND IS DELIBERATELY DEFERRED. Narrow writes
    shipped; narrow listeners did not. One onValue at `state` delivers the
    WHOLE subtree however deep the write was, so every remote change
    re-normalizes the entire structure and re-renders everything.
    DO NOT DO THIS YET. Item 25's measurement killed the case for doing it now:
    the whole synced node is 954 BYTES. The catalog isn't in it — recipes and
    ingredient config come from catalog.json over HTTPS — so the widest
    possible listener delivers under a kilobyte, and re-normalizing that plus a
    re-render is not worth a refactor that breaks four things (below).
    THE TRIGGER IS THE CATALOG MOVE. Once recipes and ingredient config live in
    the household node it is ~30 KB rather than ~1 KB, every remote change
    re-normalizes all of it, and the four costs finally buy something. Do it
    immediately after that move, not before.
    What it costs, so it isn't a surprise:
      - the atomic snapshot. Branches start arriving independently and out of
        order instead of as one coherent state.
      - pickState as written. It compares ONE updatedAt for the whole blob to
        decide local-vs-remote at launch; per-branch updates need per-branch
        stamps or a different staleness rule.
      - "is this a new household?", which today is just remote === null at the
        state node and drives the seeding path.
      - normalizeLocal splits into per-branch normalizers. That is where it
        should end up anyway, but it is work.
    Related measurement in item 25 — informative, not a gate.
    Background in FutureProjects.md ("Per-user catalog").

    UPDATE, once the catalog move shipped: the catalog went to its OWN node
    (households/{code}/catalog) with its OWN listener and its OWN updatedAt,
    not into the state node. So the ~30x growth this item was waiting for
    never lands on `state` — it lands next to it, already split. Ticking a
    checkbox still delivers under a kilobyte, and editing a recipe delivers
    the catalog without touching the list.
    That is one branch of the per-branch split this item describes, done for
    the branch that actually needed it, and it cost none of the four things
    above: each node keeps its atomic snapshot, keeps a single updatedAt that
    pickState reads unchanged, and keeps "remote === null means seed me".
    What remains open is splitting the STATE node itself (list vs plan vs
    stapleNeeds), and the case for that is still weak at 954 bytes. The next
    real trigger would be a third party in the household, not size.

    The adopt-vs-push rule is now shared. Both nodes route their listener
    through the same pickState: newer stamp wins, ties go to remote so two
    phones don't bounce a value between them, and no remote at all means
    seed. The catalog needed it for a specific reason — updateCatalog can't
    write before the listener has reported (writing early could replace a real
    catalog with a locally seeded copy), so an edit made offline sits on disk
    unwritten, and adopting on connect would silently discard it. A pristine
    seed carries updatedAt 0 precisely so it can never win that comparison;
    only an actual edit stamps a real time.

22. Move list-building logic out of the tabs and into lib.js. PantryTab is 758
    lines, MealsTab 696, ListTab 593 — all past the point where a diff is
    reviewable, and all mixing data logic with rendering. Extracting the logic
    shrinks the file AND makes it testable under 19, so it pays twice. The
    usedInRecipes extraction in Refactor notes is the pattern to copy.

23. Give ingredients a stable id. The key is norm(name), so renaming an
    ingredient orphans every reference to it — recipes, list.checked,
    list.bought, stapleNeeds, configOverrides. Item 15 shipped the suggestion
    layer that steers recipes onto canonical norm(name) identities; a real id
    is what would make that structural instead of a convention the UI has to
    keep enforcing. Gets more expensive with every ingredient added.

24. Key concurrently-edited collections by id instead of using arrays.
    localRecipes, list.extras, extraStores and removedStores are arrays
    (lib.js:134-142). An array index is not a stable identity, so two phones
    appending at once collide, and neither database can address one element
    without rewriting the whole list. Keyed objects map straight onto RTDB
    paths and Firestore documents; arrays don't.

25. [DONE] Measure the wire. Two browser windows (one normal, one incognito,
    same household code in Settings), DevTools → Network → WS → Messages on
    the observing one. No phones needed; that was a wrong assumption that made
    this look harder than it is.

    MEASURED, against a99cdb8 (narrow writes) and 9678af6 (keyed collections):

      whole household state, one frame ........... 954 B
      check off an item .......................... 126-136 B
      add an item, BEFORE keyed collections ...... grew ~35 B per item, unbounded
      add an item, AFTER keyed collections ....... 126-183 B, flat
      keepalive (a bare "0", every ~45-90 s) ..... 1 B

    Frame shape, for next time:
      {"t":"d","d":{"a":"m","b":{"p":"households/<code>/state",
                                 "d":{"list/checked/milk":true,"updatedAt":...}}}}
      "a":"m" = merge (narrow multi-path update); "a":"d" = set at a path.
      {"s":"ok","d":""} is the server ACKing a write, not data.

    WHAT IT SETTLED
      - The ~30 KB figure quoted all over these notes was wrong by ~30x. The
        catalog is NOT in the synced node — it comes from catalog.json over
        HTTPS — so the household blob is about a kilobyte. Every bandwidth
        argument built on 30 KB was inflated by the same factor.
      - Narrow writes and keyed collections were still right, but for
        CORRECTNESS (two phones overwriting each other), not for bytes.
      - The listener work is NOT worth doing at 954 bytes. See item 21: the
        trigger is the catalog move, which makes the node ~30x bigger.
      - Arrays vs keyed collections showed up directly on the wire: adds grew
        without bound before, flat after. Worth re-running after any change to
        how a collection is stored.


From a week of actually using it (Aug 2026)
-------------------------------------------
Kept together rather than scattered into the tiers above, so the numbering
doesn't shift; the tier each belongs to is noted.

26. Week starts Sunday, not Monday — and make it a setting rather than a
    constant. DAYS is hardcoded in lib.js, so this is a small change to the
    array plus a place to choose. That place doesn't exist: the Settings tab is
    household sync and the publish flow, with no actual preferences section.
    Build the section first, then this is its first occupant. TIER 1.

27. Sides on a dinner. A slot is { recipeId, servings } today, so a main plus
    two sides means several recipes per slot — either an array of them or a
    main/sides split. Both feed the shopping list the same way through
    aggregateItems, which already sums the same ingredient from several
    sources, so the list side needs nothing.
    DO THIS AFTER THE CATALOG MOVE. It changes the shape of a plan slot, and
    doing it first means migrating that shape twice. TIER 3.

28. [DONE] Meals that don't feed the shopping list. "We're having leftovers" or
    "we already have everything for this" — you want it on the plan for the
    record without its ingredients padding the list. A `skipList: true` on the
    slot, honoured in aggregateItems where the plan is walked, plus a tick in
    the picker. Cheapest of these four and probably the most used. TIER 1.

    Built as "Already have the ingredients", a checkbox on the slot's servings
    row whenever the slot is editable — next to the meal it applies to rather
    than in the picker, which is about WHICH meal, not how it's treated. The
    slot keeps its plain (not green) bubble and reads "4 sv · already have the
    ingredients" when read-only, so the week shows at a glance which meals are
    driving the shopping.

    The label names the EFFECT ("nothing to buy for this one"), not one reason
    for it. "Not on the shopping list" described the mechanism, and leftovers
    are only one of the ways a meal gets there. The stored field stays
    `skipList` — that is what it does to the data.

    Two aggregation walks read the plan — aggregateItems for the items and
    servingsByRecipe for the List tab's "N meals selected" — and both are
    list-facing, so both honour the flag through one shared `slotFeedsList`
    predicate. plannedMealCount deliberately does not: a skipped meal is still
    a planned meal, so it still counts toward "2 meals planned" and toward
    whether the week is in the "shopping" stage.

    Unticking DELETES the key rather than storing `skipList: false`, so a plan
    that never uses the feature keeps exactly the shape it always had and
    writes nothing extra. Re-picking a meal into the slot clears the flag too —
    "already have the ingredients" was about the meal being replaced.

29. Return to top on the Meals tab, or keep the search + filter row fixed. Fine
    at 30 recipes, unusable at 300 — you scroll for a while and then have to
    scroll all the way back to search again. Sticky controls solve it without
    adding a control. TIER 1.

30. Warn when another device is running an older build. Two phones on the same
    household diverged this week, and the only signal either gave was "Synced",
    which means the socket is connected and nothing about whose data won. Stamp
    each write with the build id already shown in Settings, and let a newer
    build say "another device is on an older version" when it sees an older
    stamp. An old build can't warn about itself — but the new one can warn
    about it, which is enough. TIER 4.

    Context, because it looked worse than it was: neither phone was old enough
    to do whole-state writes. The likely cause was #39's migration, which makes
    each device do ONE full set() the first time it writes after updating, to
    replace the old array shape. Both phones did that at about the same time
    and one overwrote the other. Known and accepted at merge time, spent once
    per device, and not recurring — but it took reading build stamps off two
    phones to establish that, which is what this item is for.


Refactor notes
--------------
[DONE] App.jsx was split so each feature edits a small, reviewable surface:
  - theme.js + ui.jsx: UI primitives (colors, fonts, Btn, Seg, Stripe, inputStyle)
  - lib.js: pure helpers (constants, catalog/config normalization, storage,
    model normalization, list aggregation)
  - src/tabs/*.jsx: per-tab components (List, Meals, Week, Pantry, Settings)
App.jsx itself is now ~265 lines, just wiring the tabs together.

[DONE] `usedInRecipes(data, key)` centralized in lib.js. PantryTab.jsx's three
inline copies of `data.recipes.filter/some((r) => r.ingredients.some((i) =>
norm(i.name) === key))` — the rename-affected-recipes check, the remove-item
safety check, and the item 9 "used in" display — all call it now.

UI density — Ingredients row [DONE], List row still open.
The Ingredients gear panel had become a flat pile of unrelated concerns, and
its aisle grid rendered one input per store (5, shown even where the item
isn't sold), so adding a store widened every ingredient's panel. Fixed by:
  - showing only the default store's aisle, with the rest behind an
    "Aisles at N other stores" reveal — the panel no longer grows with the
    store list
  - grouping the panel into "Where it lives" (store + aisles) and "What it
    is" (staple, used-in, rename) instead of one flat stack
The Meals and Ingredients control rows also collapsed to search + a single
Filter button + the primary action, which fits one line on a phone.

Still open: the List row (checkbox, name, staple tag, qty, store select,
info) carries the same pressure. The fix there is the same shared pattern —
"a row with a few primary bits and a details panel" — so it's worth doing as
one pass rather than a one-off.
