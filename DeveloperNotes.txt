Grocery Run — Roadmap
=====================

What is still open. Ten items, none of them urgent — this app does its job.

THE NUMBERS ARE IDs, NOT POSITIONS, AND ARE NEVER REUSED OR REASSIGNED. They
were allocated chronologically, so a low number here means the item is OLD and
still open, not that it matters more. They are referenced from code comments,
commit messages and tests/fixtures/README.md, so renumbering would silently
break every one of those. Items are listed in numeric order because that is
what makes one findable; for what to do next, use the list below.

FINISHED WORK LIVES IN DeveloperNotes-Completed.txt, and most days that is the
more useful of the two: it records WHY the app is the way it is, which is what
you need before changing something that looks odd. Search it before altering
anything surprising, and before redoing anything — several entries record
something tried, measured and rejected. A gap in the numbering here means the
item is finished and lives over there.

HOW TO READ AN ENTRY
--------------------

Each says what the thing is, why it has not been done, and WHAT WOULD CHANGE
THE ANSWER. That last part is the point, and it is what to write when adding
one. When you finish an item, MOVE ITS ENTRY to DeveloperNotes-Completed.txt
rather than marking it [DONE] here — leaving them in place is exactly how this
file reached 5,886 lines with ten live items in it.


18. EXPORT TO / LINK WITH A GOOGLE CALENDAR, keyed off the household.
    Never started, never argued about. Would want a reason first: the week
    plan is already visible in the app on both phones, so what does a
    calendar add that opening the Plan tab does not?

21. THE READ HALF OF THE DATABASE SEAM.
    The write half shipped: diffPaths computes the narrowest path set, and
    CLAUDE.md carries the rule. The READ half did not. One onValue at
    `state` delivers the WHOLE subtree however deep the write was, so every
    remote change re-normalizes the entire structure and re-renders
    everything.
    DELIBERATELY DEFERRED: it costs nothing at this size, and narrow
    listeners are materially harder than narrow writes — you have to
    reassemble a consistent object from several callbacks that arrive
    separately, which is a new class of bug in exchange for a saving nobody
    can currently measure.
    TRIGGER: a household big enough that a re-render is perceptible, or a
    move off RTDB. Measure before touching it.
    ONE THING WORTH DOING SOONER, cheaply: an ESLint no-restricted-imports
    rule banning `firebase/*` outside sync.js, so the seam cannot regress
    silently. It is currently a convention held by attention alone.

30. WARN WHEN ANOTHER DEVICE IS RUNNING AN OLDER BUILD.
    Two phones diverged once and the only signal either gave was "Synced",
    which means the socket is connected and nothing about whose data won.
    Stamp each write with the build id already shown in Settings, and let a
    newer build say "another device is on an older version" when it sees an
    older stamp. An old build cannot warn about itself — but the new one can
    warn about it, which is enough.
    PREREQUISITE, NOW DONE: the stamp names a commit that actually exists.
    Stamping writes with an id nobody can look up would have made this worse
    than useless.

36. SPLIT lib.js WHEN IT MAKES A CHANGE HARD, not on principle.
    3,209 lines now, and a grab-bag: units, ingredient identity,
    aggregation, storage, write-planning, recipe parsing. Domain files
    (units.js, ingredients.js, aggregate.js, parse.js) would be genuinely
    better.
    Splitting is churn with no behaviour change, and the file has not yet
    made anything hard to do. It has roughly tripled since this item was
    written, which is worth noticing but is not by itself the trigger.
    TRIGGER: when a change is actually hard because of it — not when the
    number gets uncomfortable.

38. A NICER URL than stuart-belcke.github.io/grocery-run/.
    DECIDED: not worth a purchased domain. ~$10-15/year for something purely
    cosmetic today.
    TRIGGER TO BUY ONE: some distribution requirement forcing it — listing
    this somewhere that demands a real registered domain.
    THE FREE OPTION, if the URL is ever worth improving without paying: a
    GitHub Organization named grocery-run gets grocery-run.github.io free.
    Not a five-minute change though — it means creating the org,
    transferring the repo, renaming it to grocery-run.github.io (the exact
    name is what unlocks the root URL), and re-authorising the domain in
    Firebase Auth. Every invite link already sent would break.

98. THE TEST GAPS THAT ARE LEFT — a register, not a plan.

    to already know where to look. Ranked by what a failure would cost.

    98a. THE FOUR WRITES BEHIND A SIGNED-IN USER — leaveHousehold,
        restoreHousehold, removeMember, createInvite. The RENDERING around

    98c. THE accessDenied SEAM. The member list has two empty states and only

        NEEDS: an ACCESS_DENIED-shaped preview seam. Small.

    98d. THE householdName SEAM — permanently "" in a test, so every name-
        dependent string renders its fallback.

    98e. PROSE HELD TO CODE. help.js describes behaviour; nothing checks the

    NOT LISTED BECAUSE THEY ARE FINE: the pure layer (345 unit tests), the

101. MAKING A HOUSEHOLD IS A FIRST-RUN-ONLY ACTION, AND THAT IS NOW ODD.
    Asked while reading Settings: "if you can get invited to multiple, why
    not be able to make new ones?" The asymmetry is real rather than
    intended — left over from when a device had exactly one household.
    Settings can SWITCH between households, RESTORE a deleted one and JOIN
    one by invite, but cannot make one. So an account accumulates households
    only by being invited, which is backwards.
    WHY IT IS NOT A ONE-BUTTON JOB:
      - CLAIMING IS THE DANGEROUS BIT. Items 83, 84 and 85 are three rounds
        of "the app made me a household I did not ask for". A Create button
        re-opens exactly that surface, so it has to be deliberate and
        confirmed, landing you IN the new household rather than quietly
        seeding one.
      - IT NEEDS A NAME AT BIRTH. A second and third household called
        home-xxxxxxxx is unreadable in the switcher.
      - WHAT DOES IT START WITH? Empty, or a copy of the starter catalog?
        Both are defensible and they are different products.
    TRIGGER: a second real household existing to want. Two people, two
    phones, one household today.

102. PER-DEVICE VERSUS PER-HOUSEHOLD SETTINGS, a distinction the app makes
    but never says out loud. Everything under Preferences is the
    HOUSEHOLD'S — units and week start live on the catalog node, decided so
    that two phones cannot disagree about what the plan grid means.
    But the app already has per-device state and does not call it settings:
    the home-screen dismissal, the seen-set of announced households, the
    device's own household code, the caches. None is exposed or labelled as
    belonging to this phone rather than everybody.
    THE QUESTION TO ANSWER FIRST is which side each setting belongs on, and
    UNITS IS THE ARGUABLE ONE — one person reading metric while the other
    reads standard costs nothing, because it changes how a total is
    displayed and not what it means. Week start is not arguable.
    TRIGGER: revisit alongside 101; they are the same conversation.

106. IMPORT A RECIPE FROM A LINK — THE APP HALF IS BUILT; ONE STEP IS LEFT
    AND IT CAN ONLY BE DONE ON A PHONE.
    Asked as: "other grocery apps parse recipes from links, is that
    achievable for us?" Items 109 and 110 settled the two assumptions under
    it; the receiver shipped with this entry. Where it stands:

      PASTING THE PAGE'S TEXT WORKS TODAY and is still the supported path —
        no length limit, and it is what item 110's five real sites made
        reliable. Worth stating first, because "you cannot paste a link" got
        heard once as "you cannot paste", which is the opposite of true.
      THE APP CANNOT TAKE A URL AND NEVER WILL. A browser refuses to read
        another site's HTML and no app-side code changes that.
      THE APP-SIDE RECEIVER IS DONE. A URL of the form
        `#chars=<n>&import=<encoded text>` opens the Meals tab with the
        recipe editor already filled, through the same fillDraft the paste
        panel uses. parseImportHash / importUrl in lib.js are the one
        definition of the format. Seven browser tests, five mutations, all
        caught. RecipeImportShortcut.md carries the whole thing.
      THE SHORTCUT IS SPECIFIED BUT NOT BUILT. Seven actions, written down in
        RecipeImportShortcut.md — Receive URLs, Get Contents of URL, Count
        Characters, URL Encode, Text, Open URLs. UNVERIFIED: there was no iOS
        device where it was written, and Shortcuts renames actions between
        versions. The ORDER is the part that matters.

    WHAT IS ACTUALLY LEFT: build those seven actions on a phone, share one
    recipe through it, and see what happens. That is the whole remainder.

    AND THE MEASUREMENT IT EXISTS TO TAKE. A page is 5-12k characters, 7-17k
    once URL-encoded, and NOBODY HAS MEASURED what iOS does with a URL that
    long. So the format declares the length BEFORE the text: truncation
    removes the tail, the count survives it, and the app says "this arrived
    cut short, 8,900 of 11,162 characters" rather than quietly importing
    three quarters of a recipe — which parses cleanly, looks finished, and is
    found out in the shop. THE LIMIT DID NOT NEED DECIDING IN ADVANCE, which
    is the answer to the question this item used to open with.
    WRITE THE NUMBER DOWN HERE when it happens. It is the only evidence
    anybody will ever have of where the real limit is, and it decides whether
    this survives or falls back to the clipboard (Copy to Clipboard instead
    of Open URLs; less magical, no limit at all).

    BE HONEST ABOUT THE GESTURE: even finished, this is not "paste a link
    into the app". It is open the recipe in Safari, Share, tap the shortcut,
    and the app opens filled in. That is a different thing from what the
    question asked for.

    THE SERVER OPTION WAS MEASURED ON 2026-08-24, and BOTH of the things it
    was rejected for turned out to be wrong. Five fixture URLs fetched from a
    GitHub Actions runner (Azure datacenter IP) — the same class of address a
    Worker uses, which is what item 109 predicted would be blocked:

      HOST                          STATUS   BYTES   Recipe JSON-LD
      www.allrecipes.com            402        612   —
      babyfoode.com                 200     679929   yes
      www.themediterraneandish.com  200     634950   yes
      www.olivetomato.com           200     473252   yes
      www.averiecooks.com           200     783278   yes

      FOUR OF FIVE SERVE A DATACENTER IP FINE. The prediction held for one
      site only.
      ALLRECIPES IS A POLICY BLOCK, NOT BOT DETECTION, and that distinction
      decides whether it is worth fighting. The 402 body is a People Inc.
      notice pointing at contentlicensing@people.inc. They are selling this
      access. No user agent, header or proxy is the answer; it will not be
      worked around, and pasting the page stays the route for that site.
      THE JSON-LD IS THERE, AND IT IS REAL. Item 109 could not see it —
      Shortcuts hands back tag-stripped text, so anything in a <script> was
      invisible — and left the raw-HTML question open. It is answered: each
      of the four carries exactly ONE ld+json block with exactly ONE Recipe
      node. Not grepped, PARSED: name, recipeYield, recipeIngredient and
      recipeInstructions all printed out in full.
      THE COUNTS MATCH THE FIXTURES EXACTLY — 10, 12, 9, 22 ingredients
      against tests/fixtures/README.md's 10, 12, 9, 22.
      AND THE NAME COMES BACK, which is item 110's first open problem and the
      one rough edge a user actually feels. So does a yield for babyfoode,
      where the text parser gets nothing.

    THREE TRAPS IN THAT DATA, found by printing it rather than assuming:
      - `name` arrives HTML-ESCAPED ("Chicken &amp; Veggie"). Unescape it.
      - `recipeYield` IS AN ARRAY and IS NOT SERVINGS. babyfoode's is
        ["24","24 1\" meatballs"] — twenty-four meatballs, not twenty-four
        servings. Reading it as servings would scale a whole shopping list
        wrong, quietly. This is the one that would cost a trip.
      - THE LINES STILL NEED THE EXISTING PARSER. "1 lb ground chicken ((or
        ground turkey))", "1/2 cup carrot,  (finely shredded )" — doubled
        brackets, stray double spaces. So JSON-LD replaces the HEURISTIC HUNT
        for where the ingredient list starts and ends, which is exactly what
        item 109's scored-heading experiment failed at. It does NOT replace
        parseIngredientLine. Nothing already built is wasted.

    WHAT THIS DOES NOT CHANGE: a browser still cannot fetch a page, so this
    needs a server either way. The Shortcut stays the only route with no
    infrastructure at all. And a GitHub runner is NOT a Cloudflare Worker —
    different IPs, different reputation — so four passes are SUGGESTIVE, not
    proof. Deploy a throwaway Worker against these same five before building
    anything on it.

    REVISIT THE SERVER OPTION ONLY IF: somebody outside the two of us uses
    this, or an Android phone joins a household. The Shortcut is iOS-only and
    needs per-phone setup, which is fine for two people and wrong for any
    real number of them. The answer then is a Cloudflare Worker (~30 lines,
    free at 100k requests/day) plus an allowlist of recipe hosts so the
    endpoint cannot be used as a general proxy.

110. THE PARSER: STOPPED AT GOOD ENOUGH, and the list to resume from.
    Five real pages from five sites parse correctly — every ingredient list,
    every step list, four of five serving counts. tests/fixtures/README.md
    names each one, its URL, and the single rule it taught. That file is the
    per-site detail; this is only what is left.

    STANDING TASK: MORE CAPTURES. The intent is to hand over another batch of
    recipe links when there is time and budget for the testing. Five sites is
    where this stopped for cost reasons, not because the returns had fallen
    off — EVERY page so far broke something the previous ones did not, so
    expect the next batch to as well. Capture them the way the five were
    (Get Contents of URL -> Copy to Clipboard, nothing in between), run each
    through parseRecipeText BEFORE changing anything, and fix what the output
    actually shows.

    WHAT TO PICK UP FIRST, in the order that would teach the most:
      - THE NAME COMES BACK BLANK on all five pages. Deliberate — a blank
        field asks to be filled in and a wrong one gets saved — but it means
        typing the title every time, which is the one rough edge a user
        actually feels. Finding a title in a whole document is genuinely
        hard; the honest options are a heuristic worth measuring, or leaving
        it alone.
        AND THE SERVER ROUTE JUST HANDS IT OVER. Item 106's 2026-08-24
        measurement pulled `name` straight out of the JSON-LD on all four
        sites that serve a datacenter IP. So the honest options are now
        three, not two — heuristic, leave it, or don't solve it here at all.
      - A UK OR EUROPEAN SITE has never been tested. The parser was taught
        "500g" and "200ml" against MADE-UP lines, never a captured page —
        the same untested-assumption shape that item 109 records going wrong.
      - A PAGE WHOSE STEPS ARE PLAIN PARAGRAPHS, neither bulleted nor
        numbered. All five fixtures bullet or number theirs.
      - PER-COMPONENT INGREDIENT GROUPS beyond the two seen so far. The
        bullet rule that separates them is the newest thing in the file.
      - A BARE NUMBERED LIST WITH NO "INSTRUCTIONS" HEADING is read as more
        ingredients. Found while writing item 106's tests, on a hand-typed
        recipe rather than a captured page — all five fixtures carry the
        heading, which is why none of them caught it. It bites a PASTE of
        something somebody typed themselves, not a fetched page, so it is
        smaller than it looks. tests/e2e/specs/importlink.spec.mjs says so
        where it works around it.
      - KNOWN WRONG, RARE: "2 x 400g tins", "1 lb 2 oz", "1 tbsp + 1 tsp",
        "Juice of 1 lemon" (arguably already right — the ingredient IS a
        lemon).

    THE RULE THAT MATTERS MORE THAN THE LIST, earned twice in one session:
    A FIXTURE BUILT FROM YOUR OWN UNDERSTANDING CANNOT TEST THAT
    UNDERSTANDING — it can only agree with it. Capture the page, do not tidy
    it, and mutation-test every rule, because a green suite that was going to
    be green anyway is worse than no suite: it feels like evidence.
