12. [DONE] Suggest units as you type when adding a new ingredient — the
    conversion table first, the suggestions after.

    What shipped: a factor table in lib.js grouping units by dimension, and
    resolveAgainstBought doing cupboard subtraction in base units, so buying
    1 lb offsets a recipe asking for 16 oz. That was the costly bug — the
    item stayed on the list looking unbought and got bought twice. Amounts
    that can be added are added (1 lb + 8 oz reads 1.5 lb), and
    commonUnitFor weighs by dimension so one "can" can't outrank an lb and
    an oz that together say this is measured by weight.

    Two decisions worth keeping:
      - PROMOTION NEVER CROSSES MEASUREMENT SYSTEMS. Display picks the
        largest unit that keeps the number at or above 1 (24 oz reads
        1.5 lb, 1500 g reads 1.5 kg), but never crosses g/kg-oz/lb — the
        metric/standard setting (item 31) is what authorises that. Two
        carve-outs: pt/qt/gal convert but are never promotion targets
        (they're container sizes — 2 cups of stock reads "1 pt"); count
        units don't promote and show in the smallest unit used (a dozen
        eggs plus two is "14 ea", not "1.17 dozen").
      - US factors are defined from their exact ratios (1 lb = 16 oz, 1 cup
        = 16 tbsp) rather than via the metric base, so 16 oz and 1 lb
        compare exactly instead of leaving 0.0001 lb on the list.
    An amount with qty 0 ("salt, to taste") is kept at zero rather than
    dropped — an empty group isn't the same as a covered one.

    [DONE] The suggestion half, extended to every place a unit is typed.
    THE INGREDIENT'S OWN UNITS COME FIRST: typing a unit for garlic offers
    `cloves` before `cup`, even though cup is the household's commonest
    overall — the flat A-Z list it replaced went unused because the obvious
    answer was nine rows down. Ranked: this ingredient's units, then
    everything typed by usage, then COMMON_UNITS; prefix before substring.
    The final tiebreak is unitSuggestions' OWN ORDER, not alphabetical — a
    fresh household has no usage to rank by, and alphabetical offered "bag,
    box, bunch" ahead of "cup" and "lb".
    NO LONGER A <datalist> — those render unreliably on phones, often as
    nothing, the same reason the ingredient-name field (item 11) moved off
    one first. One <SuggestInput> in ui.jsx serves all three fields, taking
    suggestions as a prop.
    SUGGESTS, NEVER RESTRICTS: a unit nobody has used is typed and kept,
    asserted on what was PERSISTED rather than what's in the field, since a
    box that accepts text and drops it on save looks identical while typing.

13. [DONE] Pantry staples — things you own, kept off the list until you run
    out. `config[key].staple` marks one; `stapleNeeds[key]` says you're out.
    Two decisions that shaped everything after:
      - NO PARALLEL DATA STRUCTURE. A staple is an ordinary ingredient with a
        flag; "the staples list" is only ever a VIEW.

17. [DONE] Delete / log out of households, and clean up orphaned data.

    THE HOLE, measured against the real rules rather than reasoned about: a
    member could already LEAVE (the rules allowed deleting your own record),
    but the UI never offered it; a household with no members was claimable
    again BY DESIGN ("abandonment, not a back door"); but the STATE AND
    CATALOG SURVIVED the last member leaving, so anyone who still knew the
    code could claim the empty household and read everything in it.
    Confirmed on the real emulator, not inferred. A code is 13 characters of
    [a-z0-9-], not guessable, but a removed member, an expired guest, a
    screenshot or an old phone are all realistic holders of one.

    THE FIX: THE LAST ONE OUT TAKES THE DATA WITH THEM. leaveHousehold
    (sync.js) reads the member list and, if nobody else remains, deletes
    households/{code} outright. No rules change was needed — a full member
    could already delete the node; it just was never wired up.
    THE ORDER IS FORCED: `.read` requires a membership record, so the
    instant yours is gone you can't check whether anyone else remains or
    delete anything. Check-then-act is the only shape available here.
    A GUEST MAY LEAVE BUT MAY NOT DELETE the household — deleting reaches
    the catalog and week plan, which the guest role withholds. A guest who
    is somehow last out leaves the node behind and the app says so.
    ONE RACE, ACCEPTED: two members leaving in the same instant can both see
    the other and both remove only themselves. The cleanup script is the
    answer to that residue.
    Four rules tests pin the guarantees: the last member can delete the
    node, a guest cannot, a stranger cannot, and an emptied household leaks
    nothing to whoever claims the bare code next. 47/47.

    RECLAIMING THE ONES ALREADY OUT THERE CANNOT BE A BUTTON — finding an
    abandoned household means listing /households, which nothing may do
    (the denial that stops one grant exposing every household). So
    scripts/reclaim-households.mjs runs by hand with a service-account key,
    lists households shallowly, and deletes the ones with no members. Dry
    run is the DEFAULT; --delete is opt-in; it logs each household's last
    write date before removing it. No new dependency — signs its own JWT
    with node:crypto and drives the REST API. Testable against the emulator
    without a service account: 4 seeded households, 2 with members kept, 2
    orphans found by dry run and removed by --delete.

    NOT VERIFIED IN A BROWSER: the Leave button lives behind a real
    signed-in user, which only exists behind real Firebase Auth, and the
    e2e build compiles sync out entirely — same gap as invite creation
    (item 68) and redemption. What IS proved is the half that decides
    whether data is exposed: the rules, on the real emulator.

    AND THE UNTESTED HALF WAS BROKEN — which is why that caveat is worth
    writing down rather than hedging with. Reported from the preview build:
    "Leave just seems to create a new household." It did: leaving deleted
    the old node correctly, then the device rebuilt an identical household
    under a fresh code, because switching to a code with no remote state
    takes the seed path (`push` true), uploading whatever the phone was
    still holding — the household just left. The dialog promised "a fresh
    household of its own"; what shipped was a clone.
    THE FIX IS ORDERING: resetting local state and the catalog happens in
    the SAME handler as setCode, since localRef/hCatalogRef are assigned
    during RENDER — so both land together and the new household seeds from
    an empty state. forgetHouseholdCache also drops the old code's two
    localStorage copies, or the left household stays on the phone in full,
    invisible but restorable by typing the old code back in.

    STILL NOT REPRODUCIBLE IN THE HARNESS — the whole flow needs a signed-in
    user AND the household UI, which the local-only build compiles out, so
    neither the bug nor its fix can be covered by a test here. Worth its own
    item: a preview seam for a signed-in user, the way GUEST_PREVIEW_KEY
    already fakes guest-ness.

23. [DONE] Ingredients have a stable id. The key used to BE the name, so
    renaming orphaned every reference (two were already silently lost:
    list.bought and stapleNeeds were added after the rename code and never
    updated). ingredients: { ing_7f3a2b: {name, store, aisles, staple} };
    recipe lines: { ingredientId, qty, unit }.
    THE FILE STAYS NAME-KEYED — catalog.json is hand-edited and diffed in
    git; ids in it would mean inventing and matching one across two sections
    per recipe. Minted on the way in, resolved back to names on export.
    App resolves each line's id to a name when assembling `data`, so every
    tab reading i.name was untouched. Reads still accept a legacy norm(name)
    reference (expand phase); dropping that fallback is still to do.
    The migration fires from the catalog LISTENER, never at startup —
    converting offline would let a device mint ids, remap its state, then
    adopt the other phone's catalog with DIFFERENT ids and orphan
    everything. Exactly one authority converts.

    TWO BUGS FOUND BY USING IT, NOT BY TESTS — both "code written when the
    key WAS the name": four places read a key and rendered it as a name (two
    even WROTE name-keyed entries into an id-keyed catalog, which would have
    reintroduced the old shape one entry at a time); everything that turns a
    typed name into an ingredient now goes through ensureIngredientId,
    everything that displays one uses ingredientNameFor. And renaming onto
    an existing name created a DUPLICATE, impossible while the key was the
    name — the old rename merged instead, a rule dropped along with the
    key-moving it needed. Renaming now merges, repoints recipes, sums a line
    that would otherwise duplicate, and asks first since a merge deletes an
    ingredient.
    THE LESSON: the migration was correct both times; what broke was
    ordinary EDITING afterwards. A migration test that only checks the
    conversion misses this entire class.

30. [DONE — BY REMOVING A BUTTON, AFTER TWO WRONG ANSWERS.]
    KEEPING BOTH PHONES ON THE SAME BUILD.

    THE REPORT: two phones diverged, and the only signal either gave was
    "Synced" — connected, and nothing about whose data won.

    THE ITEM AS WRITTEN ASKED FOR A WARNING, on a false premise: "an old
    build cannot warn about itself." It already could. App.jsx fetched
    catalog.json on launch, on return and on reconnect, compared appBuild
    against __BUILD__, and offered "Update available — Reload now / Later".
    Every device already warned itself, with the fix one tap away.

    ATTEMPT 1, REJECTED: a dialog on the NEWER phone telling someone to ask
    the other person to reopen their app. Redundant (the stale phone was
    already told, directly, with a Reload button), unactionable (nobody can
    update someone else's phone), and it named the wrong remedy (reopening
    isn't how a new build arrives).
    ATTEMPT 2, REJECTED: a passive "Household last saved by <build>" line in
    Settings. No interruption, still not worth it — it answers WHICH BUILD
    where the question was WHICH DEVICE, is hidden exactly when both phones
    are current (the normal case, where a divergence can still happen), and
    isn't in an export.

    WHAT ACTUALLY CLOSED IT: neither warning nor reporting. A device only
    stays old because it was OFFERED THE CHANCE TO — the "Later" button on
    the update dialog. Deleting that button fixed it; a newer build is now
    taken automatically, on launch and on every return to the app.
    THE GENERAL LESSON: WHEN A MECHANISM ALREADY HANDLES SOMETHING
    AUTOMATICALLY, ADDING A NOTIFICATION ABOUT IT IS A STEP BACKWARDS. Take
    away the escape hatch instead.

    WHAT MAKES UPDATING-WITHOUT-ASKING SAFE IS THE GUARD, not the reload
    being harmless — it destroys everything in useState. useUnsavedWork
    (ui.jsx) lets a tab declare work that outranks being current: the recipe
    editor, a pasted backup in Settings. Searches and filters are
    deliberately NOT declared — sticky but expendable, and losing one costs
    a scroll rather than an evening. DECLARED BY THE TAB, not sniffed from
    the DOM — "is any input non-empty" would guess wrong now that search
    boxes are sticky, blocking updates forever on a leftover search.
    DECLINING IS NOT REFUSING FOREVER: the check re-runs on every return to
    the app, mutation-tested.
    ONCE PER BUILD, THROUGH sessionStorage — not decoration: if the service
    worker hasn't yet swapped the cached bundle, a reload lands on the same
    build and fires again, an unbreakable loop on a phone in a shop.
    sessionStorage survives a reload and not a genuine close; if it THROWS,
    don't reload, since a failure to remember must not become a loop.

    THREE BROWSER SPECS (autoupdate.spec.mjs), driven by intercepting
    catalog.json to advertise a build the bundle isn't — exactly what a real
    deploy looks like. Mutation-tested: dropping the unsaved-work guard
    fails the draft specs; dropping the retry-on-return fails the one about
    taking it afterwards.

    THE HARD GATE IS UNTOUCHED. isBuildTooOld / APP_DATA_VERSION still stops
    a WRITE when the shared catalog's shape has moved past what this build
    understands, with its own dialog — strict and dismissible-with-a-banner,
    where the soft one is neither. Keeping them separate is the point.

32. [DONE] Update detection and the write gate.
    TWO MECHANISMS, KEPT SEPARATE:
      SOFT — the site is serving a different build. A modal offering
        Reload, dismissible per build. Right for almost every release.
      HARD — the household's catalog was written by a NEWER generation.
        Writes refused, reads untouched. A shopping list you can't open in
        a shop is worse than one you can't tick items off in.
    Both are modals, not banners (a banner scrolls past); the gate also
    keeps a banner so dismissing the modal doesn't leave editing silently
    dead.
    APP_DATA_VERSION (src/version.js) is the ordinal. A build SHA says two
    builds differ, never which is newer — the gate needs its own number and
    can't reuse catalogVersion, which moves when a user presses Export.
    The fix that made any of it work: main.jsx registered the service
    worker once and never called registration.update() again, so an app
    left in memory never learned a new build existed. It now checks on
    visibilitychange and on reconnect.
    The gate seeds from the CACHED catalog as well as the live listener —
    offline the listener never fires, and "the last catalog I saw was newer
    than me" is exactly when writing does damage. isBuildTooOld answers no
    to anything unparseable and fires only on strictly greater.
    STILL UNVERIFIED: the gate firing against a genuinely old build.

    HOUSEHOLD MEMBERSHIP, done as EXPAND then VERIFY then CONTRACT (same
    discipline as the catalog move), because it's an access change two
    phones both have to survive.
      EXPAND: a signed-in account looking at a household it has the code
        for calls recordHouseholdMembership, writing
        households/{code}/members/{uid}. Grants NOTHING new yet — access is
        still the code alone. The new rule is a `.validate`, not a `.write`,
        because .write/.read only ever ADD permission deeper in the tree; a
        broad ancestor grant can't be narrowed underneath it. `.validate`
        constrains WHAT gets written regardless: auth.uid == $uid, so a
        member record can only ever be written by the account it claims to
        represent.
      VERIFY: confirmed against the live database, not by reasoning — two
        accounts each holding their own members/{uid} sibling, neither
        disturbing the other, matching timestamps to the deploy that shipped
        the code. Confirmed by four independent facts that signing in does

107. [DONE] OPENING A PR PREVIEW DELETED THE REAL APP'S OFFLINE CACHE.
    CACHE STORAGE IS PER-ORIGIN; SERVICE WORKER SCOPE IS NOT. Every worker
    on the site's origin shares one cache store, and the origin runs both
    the real app and a full build of every open PR preview — different
    builds, different cache names, and `activate` deleted every name that
    was not its OWN: `keys.filter(k => k !== CACHE).map(k =>
    caches.delete(k))`. So opening a preview wiped the real app's cache and
    vice versa, every time, by construction.
    WHAT IT ACTUALLY COST: the real app afterwards navigates offline to a
    PRECACHED "./" that no longer exists, so it doesn't open at all — in a
    shop, from a direction (the preview deploy) nobody was watching.
    THE FIX: a cache name now carries its worker's own SCOPE
    (`grocery-run:/grocery-run/pr-preview/pr-119/:hash`), and a worker only
    deletes within its own prefix. READS ARE SCOPED TOO — `caches.match`
    with no cacheName searches EVERY cache on the origin, so all three read
    paths go through `caches.open(CACHE)` explicitly.
    MUTATION-TESTED: reverting the one-line filter fails the new
    same-origin test and NOTHING ELSE — every other service-worker test
    opens one app and checks its own cache, which stayed "right" the whole
    time the other app's cache was being deleted beside it.

Hygiene — not features, and not sequenced
------------------------------------------
None of these ship anything on their own. They're what keeps the app cheap to
change: a test layer, one place for shared logic, a database seam narrow
enough to swap what sits behind it. Do them alongside whatever feature is next
rather than saving them for a cleanup that never gets scheduled.

MEASURED AND DELIBERATELY NOT PROBLEMS. Recorded so nobody optimises them on
instinct: bundle at 253 KB / 76 KB gzipped (Firebase already dynamically
imported and code-split); aggregateItems is O(recipes x ingredients) and runs
on every render, invisible at this scale — MEASURE BEFORE TOUCHING IT, since
the last time payload size was reasoned about rather than measured the
estimate was wrong by 30x (item 25).

reuse for any future shape change two devices have to survive. expand: the
new path (households/{code}/catalog) is added and read, old fields left in

    under. THE ACTUAL LESSON, kept because it is worth not re-learning: a
    host allowlist and a request-volume cap answer two different questions
    (WHERE vs HOW MANY) and were never in tension with each other — running
    both was available the whole time, not a tradeoff that needed an
    audience-size trigger to resolve.
    Verified live again with both mechanisms deployed together: a newly-
    allowlisted site (recipetineats.com) served real JSON-LD, a
    never-listed one (allrecipes.com) came back host_not_allowed without
    an actual fetch attempt, and an allowlisted site still worked
    immediately afterward — the disallowed call did not cost any of the
    caller's daily budget.

    TWO BUGS THE ALLOWLIST BROUGHT WITH IT, both found by re-reading the
    diff rather than by anything failing:

    1. HALF THE ALLOWLIST WAS UNREACHABLE. Each host went in under
    whichever spelling the discovery probe happened to fetch — 7 bare, 9
    "www." — and the check compared the raw hostname, so the OTHER
    spelling of every one of the 16 was refused. Pasting
    www.pinchofyum.com or recipetineats.com got "that site isn't set up
    for automatic import yet" for a site that IS on the list, and which
    form somebody has depends on nothing but where they copied the link.
    NOT THEORETICAL: probed all 16, and 15 serve a 301 from one form to
    the other, so both are live URLs anyone could hold; fetch() follows
    the redirect, so the two always reach the same page.
    FIXED by comparing with "www." stripped from both sides. That cannot
    widen the list — "www." is a subdomain label, not a domain boundary,
    so it only ever collapses two spellings of one registrable domain
    onto the single entry. Checked that evil.com, wwwevil.com,
    pinchofyum.com.evil.com and notpinchofyum.com all still refuse.

    2. THE RATE LIMITER COULD TAKE THE WHOLE FEATURE DOWN WITH IT. The KV
    read/write was unguarded, so an unbound binding, a KV outage or the
    free tier's own write quota would throw out of the handler, and
    Cloudflare would answer with its HTML error page instead of this
    Worker's JSON. recipeImport.js can't parse that, reports "network",
    and the app says "Couldn't fetch that page" — blaming the recipe site
    for a fault entirely on this side. SAME SHAPE AS THE OPAQUE 1042 THIS
    ITEM ALREADY HIT ONCE while probing, which is the reason it was worth
    looking for.
    FIXED by catching and FAILING OPEN. The reasoning is the load-bearing
    part: this is a throttle sitting BEHIND an allowlist, not the thing
    keeping the endpoint safe, so "let one request through uncounted"
    beats "import is broken today" — the allowlist still bounds what can
    be fetched either way. A limiter that fails closed would have been the
    wrong default for the same reason.
    BOTH VERIFIED LIVE ON ONE THROWAWAY DEPLOY WITH THE KV BINDING
    DELETED FROM wrangler.toml, which exercises the fail-open path for
    real rather than by argument: www.pinchofyum.com and
    recipetineats.com both returned real JSON-LD, and www.allrecipes.com
    was still refused.
